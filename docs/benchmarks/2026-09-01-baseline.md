# ベンチマーク 2026-09-01 — 埋め込みの基準値（Phase 0 時点）

Phase 1 に着手する前に、**埋め込み側の素の性能**を測って記録する。
検索そのもの（pgvector の距離計算・索引の有無）はまだ実装が無いので測っていない。
ADR 0007 が要求する「索引の前後を並べる」ベンチはここには**含まれない**——本書はその手前の基準線である。

## 測定環境

| 層 | 実測値 |
| --- | --- |
| GPU | NVIDIA GeForce RTX 3090 / 24576MiB / ドライバ 610.88 / CUDA UMD 13.3 / WDDM |
| CPU・RAM | 20 コア / 31GB（空き 28GB） |
| Ollama | **0.33.2**（Windows ネイティブ実行・ADR 0008） |
| モデル | `bge-m3:latest`（digest `790764642607`・F16・566.70M・**1024次元**・文脈長 **8192**・1.2GB） |
| Recall 側 | WSL2 から HTTP。Windows へのアドレスは default gateway `172.23.160.1:11434` |
| PostgreSQL | 17.11（Debian）＋ **pgvector 0.8.6**（`pgvector/pgvector:pg17`） |
| Go | 1.27.0 |

⚠️ **占有ベンチではない。** 測定時、GPU は他アプリに 5.7GB / 17% を使われていた。
専有すればこれより速くなる余地がある。**下振れ側の数字として読むこと。**

## 1. モデルの素性（実測で確認）

| 確認項目 | 結果 |
| --- | --- |
| 次元 | **1024** — ADR 0008 の記述および `RECALL_EMBED_DIMENSIONS` と一致 |
| 文脈長 | **8192** — 同上 |
| 意味の健全性 | 関連ペア 0.4861 > 無関係ペア 0.3165 / 0.3441 |

意味の健全性は、要件定義 §6.1 ③ が警告する失敗（生成モデルに数値を作文させると
**意味的な距離が保存されない**）の反対側を確認したもの。念のため毎回測る価値がある。

## 2. 🔑 ベクトルは L2 正規化済み（ノルム = 1.0）

実測: 返ってきたベクトルの L2 ノルムが **ちょうど 1.0**。

**実装上の帰結**: 正規化済みベクトル同士では**コサイン類似度と内積が一致する**。
したがって pgvector では

- `<=>`（コサイン距離）— 内部で毎回ノルムを計算する
- **`<#>`（負の内積）— 乗算と加算だけで済む**

の**どちらでも順位は同じ**になり、`<#>` のほうが軽い。

⚠️ ただし **`<#>` を選ぶことは「入力が常に正規化されている」という前提に依存する**。
埋め込みプロバイダを差し替えると（ADR 0005 が想定するとおり）この前提は保証されない。
`<#>` を採るなら、**正規化を Recall 側の責任として明示的に行う**か、
`Embedder` の契約に「正規化済みを返すこと」を書くこと。**黙って前提にしない。**

## 3. スループット（2回目の計測値を採用・1回目はウォームアップ）

| 条件 | 件数 | 秒 | 件/秒 |
| --- | ---: | ---: | ---: |
| 短文 33字 × 1 | 1 | 0.052 | 19.1 |
| 短文 33字 × 32 | 32 | 0.259 | 123.6 |
| **実チャンク相当 230字 × 1** | 1 | 0.085 | 11.8 |
| **実チャンク相当 230字 × 32** | 32 | 0.365 | **87.8** |
| **実チャンク相当 230字 × 128** | 128 | 1.370 | **93.4** |

コールドスタート（モデルのロードを含む初回）= **18.4 秒**。

### 🔑 バッチ化が 8倍効く。取り込み経路は必ずまとめて送ること

同じ 230字のチャンクで **1本ずつ 11.8 件/秒 → 32本まとめて 87.8 件/秒**。

10万チャンクの取り込み時間に直すと:

| 送り方 | 見積り |
| --- | --- |
| 1本ずつ | **約 2時間21分** |
| 32〜128本ずつ | **約 18分** |

⇒ **取り込み経路をナイーブに「1チャンク1リクエスト」で書くと、8倍の時間を払う。**
Phase 1 の 2番（Ollama クライアント）を書くとき、`Embedder` の呼び出し側が
バッチを渡せる形になっているかを最初に確認すること。

⚠️ 128本は 32本に対して +6% しか改善していない。**32本前後で頭打ち**なので、
バッチを無闇に大きくしてもメモリを食うだけである。

### 短文の数字を取り込み見積りに使わないこと

短文（33字）は 123.6 件/秒 出るが、**実データのチャンクはもっと長い**。
230字で 87.8 件/秒＝**約3割落ちる**。要件定義の見積りには**長いほうの数字を使う**。

## 4. ⚠️ 検索1回あたりの埋め込みコストは 52〜85ms

クエリの埋め込みは必ず**1本**（バッチ化できない）ので、上表の「×1」がそのまま検索の固定費になる。

要件定義 §8 の性能要件は

> 1万チャンクに対し検索 p95 < 200ms（**埋め込み往復を除く**）

だが、**利用者から見た応答時間はこの 52〜85ms を含む**。
つまり 200ms の予算を満たしても、体感は 250〜285ms になる。

🔑 ADR 0009 が `p95 latency` を「**埋め込み往復を含む／除く の両方**」で測れと書いているのは、
この差を隠さないためである。**片方だけ報告しないこと。**

## 5. エンドツーエンドの疎通（pgvector まで）

日本語4文を bge-m3 で埋め込み → `vector(1024)` 列へ格納 → 1件のクエリで `<=>` 検索した。

**入力（これが投入した本文そのもの。末尾の句点を含む）:**

```
D1  pgvector は PostgreSQL にベクトル型と距離演算子を足す拡張である。
D2  HNSW 索引は近似最近傍探索を高速化するが、再現率と引き換えになる。
D3  確定申告の期限は毎年3月15日である。
D4  味噌汁の出汁は昆布と鰹節でとるのが基本。

Q   ベクトルの索引を張ると検索は速くなるか
```

**類似度の定義:** `1 - (e <=> q)`（pgvector のコサイン距離の補数）。
bge-m3 の出力は L2 正規化済み（§2）なので、**素の内積と一致する**。

| 順位 | 文書 | 類似度 |
| ---: | --- | ---: |
| 1 | D2 | 0.5738 |
| 2 | D1 | 0.5054 |
| 3 | D4 | 0.3182 |
| 4 | D3 | 0.2685 |

関連2件と無関係2件が分離している。**Ollama → Go → pgvector の経路が通ることを確認済み。**

⚠️ これは4件の疎通確認であって**検索品質の評価ではない**。
品質は ADR 0009 の正解セットで `recall@k` と `MRR` を測るまで語らないこと。

### 🔴 追記（2026-09-02）: 本節は一度、再現できない形で書かれていた

初版のこの表は、**投入した本文ではなく画面に出た本文を手で書き写したもの**で、
**4行とも末尾の句点「。」が落ちていた**。表から本文を読み取って再実行すると別の入力になる。

recall レーンが再現を試みて不一致を報告し、原因を追った（実測）:

| 入力 | 類似度 |
| --- | --- |
| **上の入力（句点あり）** | **0.5738 / 0.5054 / 0.3182 / 0.2685** ＝ 初版の記録値と一致 |
| 初版の表のセルのまま（句点なし） | 0.5899 / 0.5165 / 0.3440 / 0.2804 |

⇒ **記録された数字は正しく、文書が間違っていた。** 本節は「入力」を書いたつもりで
「出力」を書いていた。

🔑 **副産物のほうが実装に効く（recall レーン発）——末尾の句点1文字がコサイン類似度を
0.016 動かす。** これは `recall@10` の判断に使うゆらぎ（0.017）と**同じ桁**である。
⇒ **チャンク分割で末尾の句読点を落とすかどうかは、検索品質に効く実装判断。**
取り込み側と評価セット側で扱いが違うと、原因の分からないスコア差になる
（`testdata/eval/corpus.jsonl` は句点を保持している）。

⚠️ 原因の特定には**2回の否定**が要った。1回目の仮説（ベクトルを SQL リテラルへ 6桁で丸めた）は
実測で1桁も動かず、2回目（34字で切り詰めた）は**方向は正しかったが機構が違った**
（表のセルは元の 35 / 43 / 20 / 19 字に対して **34 / 42 / 19 / 18 字**＝一律に1文字短い）。
★ **もっともらしい説明を、測らずに採用しない。方向が合っている説明ほど、
機構まで確かめずに通り抜けやすい。**

## 7. 再現手順

```bash
# 埋め込み
curl -s http://<Windows>:11434/api/embed \
  -d '{"model":"bge-m3","input":["文1","文2"]}' | jq '.embeddings[0] | length'   # => 1024

# pgvector
docker compose up -d
docker compose exec -T db psql -U recall -d recall -c "CREATE EXTENSION IF NOT EXISTS vector;"
```

⚠️ `<Windows>` は WSL の default gateway（測定時 `172.23.160.1`）。
**WSL を再起動すると変わる。** `ip route` で取り直すか、`.wslconfig` の
`networkingMode=mirrored` で `localhost` に固定する。

## 追記: §5 の絶対値は再現しなかった（2026-09-01・API 開通時に判明）

Ollama クライアントと API の配線が完了し、`POST /v1/search` で §5 と同じ4文・同じクエリを
実行したところ、**順位は完全に一致したが類似度の絶対値が違った**。

| 順位 | 本文 | §5 の記録 | 再測定 |
| ---: | --- | ---: | ---: |
| 1 | HNSW 索引は近似最近傍探索を高速化するが、再現率と引き換えになる | 0.5738 | **0.5899** |
| 2 | pgvector は PostgreSQL にベクトル型と距離演算子を足す拡張である | 0.5054 | **0.5165** |
| 3 | 味噌汁の出汁は昆布と鰹節でとるのが基本 | 0.3182 | **0.3440** |
| 4 | 確定申告の期限は毎年3月15日である | 0.2685 | **0.2804** |

### どちらが正しいか — 実装側が正しい

Ollama を直接叩いて**素の Python でコサイン類似度を計算**したところ、
`0.5899 / 0.5165 / 0.3440 / 0.2804` で **API が返す `vector_score` と4桁一致**した。

### ずれの原因は特定できなかった（同一性は全て確認済み）

| 疑ったもの | 実測 |
| --- | --- |
| モデルが変わった | digest `790764642607` — §5 の記録と**一致** |
| Ollama の版が変わった | `0.33.2` — §5 の記録と**一致** |
| 埋め込みが非決定的 | 同一入力2回で要素差 **0**（決定的） |
| エンドポイント差（`/api/embed` と旧 `/api/embeddings`） | 旧は非正規化（ノルム 26.56）だが**コサインは尺度不変で同値** |
| バッチ化がベクトルを変える | 下記のとおり**変えない** |

⇒ **§5 の絶対値は、文書に書かれた手順からは再現できない。** 順位（関連2件が上位・無関係2件が下位）は
再現するので、§5 の結論「Ollama → Go → pgvector の経路が通る」は有効なまま。
**以後、絶対値の基準線には §5 ではなくこの追記の数値を使うこと。**

### 🔑 教訓: 疎通確認の数値でも、入力と計算式をそのまま残す

§5 は入力文とクエリを本文に書いているが、**類似度をどの式で出したか**を書いていない。
モデルもランタイムも一致しているのに再現できないのは、記録がその一点を欠いているからである。
測定値が正本であるリポジトリでは、**後から検証できない数字は正本になれない。**

### 副産物: バッチ化はベクトルを変えない（実測）

| 比較 | 最大要素差 |
| --- | ---: |
| 1本単独 vs 長文と混ぜた2本バッチ | **0.000** |
| 1本単独 vs 32本バッチ | **0.000** |

パディングやプーリングの影響が無いことを意味する。
⇒ **取り込みを32本バッチ、検索クエリを1本で埋め込んでも、両者は同じ空間で比較できる。**
バッチ化（8倍の高速化）が検索品質を損なわないことが実測で裏付けられた。

### 残リスク: `embedder_id` はモデルの版を区別しない

`Embedder.ID()` は `bge-m3:1024`（モデル名＋次元）であり、**digest もランタイム版も含まない**。
同じタグで別の重みが引かれても ADR 0005 の不一致検知は発火しない。
今回はどちらも一致していたので原因ではないが、**検知網に穴があること自体は事実**である。
digest を `embedder_id` に含めるかは、再取り込みの頻度と併せて別途 ADR で判断する。
