# 評価 2026-09-01 — ベクトル検索のみの基準線

ADR 0009 が Phase 1 の必須要件と定めた検索品質の評価。**語彙検索を実装する前の基準線**であり、
以後の Q-1（tsvector か BM25 か）・Q-2（bigram か形態素か）・Q-3（`alpha` の最適値）の判断は、
すべてこの数値との差分で行う。

生データ: [`data/2026-09-01-eval-baseline.json`](data/2026-09-01-eval-baseline.json)
（**集計値はすべて per-query の生データから第三者が再計算できる**）

## 条件

| 項目 | 値 |
| --- | --- |
| git revision | `70a4c04`（変更なし） |
| 埋め込み | `bge-m3:1024` / Ollama 0.33.2 / digest `790764642607…` |
| ストア | PostgreSQL 17.11 + pgvector 0.8.6・**索引なし（全探索）** |
| 評価セット | 259チャンク（19ファイル・平均327字）/ **56クエリ** / 正解 延べ222件 |

⚠️ 占有ベンチではない（GPU は他アプリと共有）。

### 🔑 評価セットは判別力を持っている

`README.md` の自己点検条項「`recall@10` が 0.95 を超えたら測定器の故障を疑う」に対し、
実測は **0.605**。**改善の余地が約4割**あり、語彙検索・ハイブリッド合成・reranker の
効果を測れる状態にある。満点に近い評価セットは何も語れないので、この値は健全である。

`MRR = 0.730` は「最初の1件はだいたい1〜2位に来る」ことを意味する。
つまり**上位1件の妥当性は高いが、関連チャンクを網羅的に集める力が弱い**。
引用付きで答えるという用途（要件定義 §2.1）では後者が効く。

### 🔴 事前の予想と逆の並びになった

評価セット作成時の予想は「ベクトルは `paraphrase` / `synonym` / `orthography` に強く、
`exact-term` / `numeric` / `negation` に弱い」だった。**実測はほぼ逆である。**

- 弱いと予想した `negation`（0.77）と `numeric`（0.70）が**上位2つ**
- 強いと予想した `paraphrase`（0.44）と `synonym`（0.50）が**下位2つ**

読み方: このコーパスでは、`numeric` / `negation` のクエリも本文の語をそのまま含みがちで、
bge-m3 はその**字面の一致に十分反応している**。逆に `paraphrase` / `synonym` は設計上
本文の語彙を避けて作ってあるため、埋め込みに意味の橋渡しを要求する。
**bge-m3 はその橋渡しを、期待されていたほどは行っていない。**

⚠️ **ただしこれは仮説であって結論ではない。** 各タグ n=6〜8 なので、1クエリの成否で
recall は約 0.14 動く。`paraphrase` 0.44 と `negation` 0.77 の差（0.33）は1クエリ分の
ゆらぎより大きいが、**総合値1本での優劣判定を禁じる**（`testdata/eval/README.md`）規則は
タグ別にも適用される。次の判断材料にはするが、根拠として引用するときはこの注記ごと引くこと。

### ⚠️ 戦略への含意（要検証）

語彙検索（項目4）が埋められるのは主に `exact-term` の取りこぼしだが、
**最大の穴である `paraphrase` 0.44 は語彙検索では埋まらない**。字面が違うことが
そのカテゴリの定義だからである。もしこの傾向が語彙検索実装後も残るなら、
Q-1/Q-2 の選択よりも**埋め込みモデルの選択か reranker（Q-4）のほうが効く**可能性がある。
Q-4 は「Phase 1 は入れない」と決めてあるが、**その判断はこの数字を見る前のものである**。

## 上位10件に正解が1件も入らなかったクエリ（7件）

| tag | クエリ | 正解数 |
| --- | --- | ---: |
| `exact-term` | pgvector 0.8.6 | 1 |
| `exact-term` | RECALL_STORE | 4 |
| `particle` | Recall が Corpus を呼ぶことはあるか | 4 |
| `compound` | 再取り込み | 2 |
| `orthography` | クオリティゲートには何が含まれるのか | 3 |
| `synonym` | 速さと当たり具合のトレードオフ | 4 |
| `paraphrase` | 同じ問い合わせを繰り返しても順位は変わらないのか | 2 |

`Recall が Corpus を呼ぶことはあるか` は**意図的に作った最小対**（`Corpus が Recall を呼ぶ` と
内容語が共通で正解集合が交わらない）で、予想どおり片方が構造的に落ちた。
ベクトル検索が語順・格関係をほとんど見ていないことの直接的な証拠になる。

## 数字の読み方（`testdata/eval/README.md` の規則を再掲）

- 56クエリなので、1クエリの成否で総合 recall は約 **0.018** 動く。**±0.02〜0.04 の差は判断材料にしない**
- タグ別は n=6〜8 なので1クエリで約 **0.14** 動く。カテゴリ単位で複数クエリが動く変化だけを見る
- 判断に使ってよいのは (a) 大差 (b) カテゴリ別の一貫した傾向 (c) per-query の差分リスト
- `p95` は 280 サンプル。GPU の占有状況で揺れる

## 規模の限界

このコーパスは 259 チャンクで、要件定義 §8 の「1万チャンクに対し p95 < 200ms」の
検証には**ならない**。`p95`（埋め込み除く）3.3ms は「索引なし全探索・259チャンク時点」の値であり、
規模の性能検証と HNSW の判断は Phase 1 項目7 の仕事である（ADR 0007）。

また、コーパスは ADR・規約文書であり `pgvector`・`HNSW`・`org_id` のような識別子が濃い。
**一般の日本語文書に外挿しないこと。**

## 再現手順

```bash
docker compose up -d
set -a; . ./.env; set +a          # RECALL_DATABASE_URL と RECALL_OLLAMA_URL が要る
make eval GPU_NOTE="占有状況を書く"
```

⚠️ `make eval` は `make check` に含まれない（CI に Ollama が無く、評価は検査ではなく計測だから。ADR 0013）。
