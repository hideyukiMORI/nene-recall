## 0. 🔑 bigram 側を同一セッションで測り直した（指示からの逸脱）

指示は「bigram 側は既存の正本（`2026-09-02-eval-pg-lexical-only-r5.json` ほか・別セッション）を再利用する」だった。
**そのとおりにすると latency の比較が成立しないことが測定中に分かった**ので、bigram 側 8点を同一セッションで測り直した。

理由は §5 にある——**同じ bigram・同じコードで測っても、系統2（埋め込み往復を除く）の p95 は
セッション内で 6.9ms と 14.7ms の間を動く。** 別セッションの 14.4ms と本日の kagome の 8.6ms を並べると
「分割器で下がった」ように見えるが、その差はセッション（あるいは run 間のばらつき）だけで説明できてしまう。

**品質指標のほうは、再測が既存の正本と完全に一致した。**

| 構成 | 正本（別セッション） | 本測定の統制 | 上位10件の並びが違うクエリ |
| --- | ---: | ---: | ---: |
| bigram 語彙のみ `recall@10` / `MRR` | 0.6198686371100164 / 0.7359195402298851 | **同値** | **0 / 58** |
| bigram ハイブリッド 0.8 `recall@10` / `MRR` | 0.7240763546798030 / 0.8071839080459772 | **同値** | **0 / 58** |

⇒ **順位付けは決定的で、リビジョン `b3f1a64` → `f7a896a` の間の変更は bigram の順位を1件も動かしていない。**
以降の品質の比較には、この統制（同一セッション）の値を使う。正本の値と一致しているので、どちらを使っても同じである。

### 🔴 `exact-term` の下降は「識別子の隣接が緩む」経路では説明できない

`internal/store/postgres/lexeme_roundtrip_test.go` の `TestLexemeRoundTripLosesAdjacencyWithMorphemes` は、
**助詞を捨てる分割器では `RECALL_STORE` のような識別子の隣接判定が緩む**（`recall は store` が
`lexeme_text` 上で `recall store` になり、`recall <-> store` に当たってしまう）ことを固定している。
この経路が効いているなら、識別子を含むクエリで**偽ヒットが増える**はずである。

**実測ではその経路は1件も観測されていない。**

1. **下降した `exact-term` は `q-002` だけで、そのクエリは `_` / `.` / `-` を持つ識別子を含まない。**
   クエリは `` `<#>` 演算子は何を計算するのか `` で、**`<#>` は両方の分割器がトークンを1つも作らない**
   （bigram の出力は `演算 算子 子は は何 …`、kagome は `演算 子 何 計算 する の`）。
   落ちた gold は `bench-embed#003`。⇒ 隣接ではなく `ts_rank` の並びの変化である
2. **識別子を含むクエリ 9件は、下がったものが1件も無い。**

   | query | tag | 語彙のみ recall（bigram → kagome） |
   | --- | --- | --- |
   | `q-001` `pgvector 0.8.6` | `exact-term` | 1/1 → 1/1 |
   | `q-003` `RECALL_STORE` | `exact-term` | 4/4 → 4/4 |
   | `q-004` `modernc.org/sqlite` | `exact-term` | 4/4 → 4/4 |
   | `q-005` `CNF-001 は何を禁止する検査か` | `exact-term` | 4/4 → 4/4 |
   | `q-006` `voyage-4-nano` | `exact-term` | 2/2 → 2/2 |
   | `q-007` `PdoChunkSearchRepository.php` | `exact-term` | 1/7 → 1/7 |
   | `q-019` `org_id に既定値を置いてはいけない理由` | `negation` | 4/5 → 4/5 |
   | `q-022` `pgvector-go を依存に…` | `negation` | 2/4 → **4/4** |
   | `q-048` `0.7 という数字に裏付けは…` | `synonym` | 1/7 → **2/7** |

3. **`q-003`（`RECALL_STORE`・テストが再現している当のクエリ）で、語彙スコアが 0 でない行は
   両方とも同じ4件**（`claude-md#005` / `requirements#005` / `claude-md#009` / `adr-0007#004`・すべて gold）。
   5位以下は両方とも `lexical_score = 0.000000` である。⇒ **この評価コーパスには
   「`recall` と `store` が機能語だけを挟んで並ぶ」チャンクが無く、経路が発火する条件が揃っていない。**

⚠️ **したがって本測定は、あの経路が無害であることを示していない。** 示しているのは
「**このコーパスでは発火しなかった**」だけである。テストが固定しているのは実装の性質であって、
コーパス依存の観測ではない。

0.9→0.721/0.7211・0.95→0.666/0.6656）。`alpha=0.85` は rounds=1 の掃引に無かった点で、本測定が足したものである。

⚠️ **`MRR` はすべての `alpha` で kagome のほうが低い**（差 −0.022〜−0.037）。
`recall@10` の順序（kagome が上）と `MRR` の順序（bigram が上）が全点で逆である。

⚠️ **プラトーの幅は1クエリ（0.017）と同じ桁の差で決まっている。** `alpha=0.7` の bigram は
最大から −0.0158、kagome は −0.0267。**この2つを分けているのは 0.6 クエリぶんの差**である。

### 系統1（埋め込み往復を含む）

bigram p50 57.60〜62.42 / p95 68.37〜81.14、kagome p50 52.63〜58.86 / p95 64.81〜69.98。

GPU を他アプリと共有しているぶんのばらつきを含む。

### 予想との突き合わせ

予想は「トークン数が減るので `tsvector` が小さくなり、**埋め込みを除く p95 は下がる**（14.4ms → 10ms 前後）」。

| 予想の部分 | 実測 | |
| --- | --- | --- |
| `tsvector` が小さくなる | **チャンクあたりの相異なるレキシーム数 111.1 → 53.5（48%）・`tsvector` の実バイト数 1414 → 694（49%）** | ✅ 的中 |
| 系統2 の p95 が下がる | モードを揃えた比較で、低モード・高モードとも kagome が低い | ✅ 向きは的中 |
| 14.4ms → 10ms 前後 | **この形では確認できない。** 同じ bigram が同一セッションで 6.91〜14.72ms を出す | — |

レキシーム数は評価用 DB を直接見た値である（`recall_eval` は `make eval` が毎回作り直す）。

```sql
SELECT tokenizer_id, count(*) AS chunks,
       round(avg(length(lexemes))::numeric,1) AS avg_lexemes,
       min(length(lexemes)) AS min_lexemes, max(length(lexemes)) AS max_lexemes,
       round(avg(octet_length(lexemes::text))::numeric,0) AS avg_tsvector_bytes
FROM chunks GROUP BY tokenizer_id;
```

| `tokenizer_id` | chunks | 平均レキシーム数 | 最小 | 最大 | 平均 `tsvector` バイト |
| --- | ---: | ---: | ---: | ---: | ---: |
| `bigram:nfkc-lower:v1` | 259 | 111.1 | 6 | 313 | 1414 |
| `kagome:ipadic:ascii-words:v1` | 259 | **53.5** | 3 | 135 | **694** |

⚠️ `length(tsvector)` は**相異なるレキシームの数**であって、生成したトークンの総数ではない。

## 7. この数字の限界

- **モードの原因が不明**（§6）。同一バイナリ・同一データ・連続実行で系統2 が約2倍に割れる。
  本測定は原因を切り分けていないので、**latency の絶対値をここから外挿しないこと**
- **規模**: 259チャンク・**索引なしの全探索**（ベクトルも `lexemes` も）。
  分割器を変えるとレキシーム数が半分になるが、**GIN 索引を入れた構成では効き方が変わりうる**。
  10万件は Phase 1 項目7（ADR 0019 の紛れ込みコーパス）の仕事である
- **58クエリ・タグ n=6〜8**。総合 `recall@10` は1クエリで 0.017、タグ別は1クエリで 0.14 動く。
  §3 で「差」と呼んだもののうち、1クエリぶんを超えているのは
  **`paraphrase`（+0.18・実体は 5件の gold）と `orthography`（−0.18・実体は 6件の gold）だけ**である
- **コーパスの偏り**: ADR・規約文書で `pgvector` / `org_id` / `CNF-001` のような識別子が濃い。
  ADR 0018 Decision 2 の「ASCII 語は1語」規則はこの偏りに最も強く効く規則であり、
  **一般の日本語文書では bigram との差の出方が変わりうる**（`testdata/eval/README.md` の限界節）
- **辞書は IPA だけ**。UniDic・表層形・助詞を残す版（ADR 0018 の却下表にある v2 候補）は測っていない
- **`orthography` タグの下降は、そのタグの作られ方に依存する。**
  このタグのクエリは `ハイブリット` / `ポスグレ` のようにわざと表記を崩したもので、
  **形態素解析器にとっては未知語**である。一般の表記ゆれ（送り仮名・全半角）の話に一般化しないこと
- **占有ベンチではない**: GPU は他アプリと共有。系統1 のばらつきはその反映
- 🔴 **`TestLexemeRoundTripLosesAdjacencyWithMorphemes` の経路は、このコーパスでは発火しなかっただけである**（§4）

## 8. 再現手順

```bash
docker compose up -d
set -a; . ./.env; set +a
for a in 0 0.5 0.6 0.7 0.8 0.85 0.9 0.95; do
  make eval EVAL_LABEL=kagome-$a EVAL_ALPHA=$a EVAL_ROUNDS=5 \
       EVAL_TOKENIZER=kagome GPU_NOTE="占有状況を書く"
  make eval EVAL_LABEL=bigram-$a EVAL_ALPHA=$a EVAL_ROUNDS=5 \
       EVAL_TOKENIZER=bigram GPU_NOTE="占有状況を書く"
done
```

⚠️ `make eval` は `make check` に含まれない（CI に Ollama が無く、評価は検査ではなく計測だから。ADR 0013）。

🔑 **`git_modified: false` で測ること。** `make eval` の既定の出力先が `docs/benchmarks/data/` なので、
**前の測定の JSON が未追跡のまま残っていると次のビルドが `git_modified: true` で刻まれる。**
本測定は 16本すべて `EVAL_OUT` をリポジトリ外へ向けて走らせ、全部終わってから `data/` へ移した。

🔑 **latency を読むなら、片方だけ別セッションの値を使わないこと**（§0・§6）。
