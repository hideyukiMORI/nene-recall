# 評価 2026-09-02 — SQLite と PostgreSQL を同一評価セットで比較する（rounds=5）

[ADR 0007](../adr/0007-pgvector-over-brute-force.md) は pgvector を既定に選んだが、その判断の価値を
「測ってから索引を入れた経路」に置き、比較対象として**同一データで Go 側総当たり（SQLite）を並べる**ことを
成果物に数えていた。[ADR 0017](../adr/0017-sqlite-store-for-comparison.md) で SQLite ストアが入ったので、
その約束をここで果たす。

同時に、[ADR 0014](../adr/0014-lexical-search-is-tsvector-over-bigram.md) が**測らずに**却下した Go 側 BM25 に
対して「BM25 の数字は項目 8 で必然的に出る」と書いた申し送りの、品質面の答えもここで出る——
SQLite 側の語彙採点は FTS5 の `bm25()` であり、Postgres 側は `ts_rank` である。

🔴 **本書は観察だけを書く。判断（どちらを既定にするか・`alpha` をいくつにするか）は書かない。**
判断は ADR の仕事である。

# 3層に分けて読む

🔴 **2つのストアの `recall` の差を「ストアの差」と読んではいけない**（ADR 0017 Consequences）。
差には**語彙採点関数の差**（`ts_rank` と `bm25()`）が混ざっている。そこで
**純ベクトル（`alpha=1.0`）でストアの差を、語彙のみ（`alpha=0.0`）で採点関数の差を**それぞれ見る。

## 層1 — 純ベクトル `alpha=1.0`：品質は**完全に一致した**

| 構成 | `recall@1` | `recall@5` | `recall@10` | `MRR` | micro |
| --- | ---: | ---: | ---: | ---: | ---: |
| `pg-vector-only-r5` | 0.1896 | 0.4806 | **0.5960** | **0.7055** | 131/236 = 0.555 |
| `sqlite-vector-only-r5` | 0.1896 | 0.4806 | **0.5960** | **0.7055** | 131/236 = 0.555 |
| 差 | ±0.0000 | ±0.0000 | **±0.0000** | **±0.0000** | ±0 |

「一致した」は集計値だけの話ではない。**58クエリすべてで上位10件の並びが `eval_key` の順序まで同一**であり、
同じ位置に来た件の `vector_score` の差は **最大 1.19e-07・平均 3.10e-08**（float32 の丸め幅）だった。

⇒ **pgvector の `<#>` と Go 側総当たりの内積は、このデータでは同じ順位を返している。**
これは品質の主張ではなく、2つの実装が同じ計算をしていることの確認である。

🔑 **したがって層1 で観測できる差は latency だけになった。** 下の §「p50 / p95」を参照。

## 層2 — 語彙のみ `alpha=0.0`：`ts_rank` と `bm25()` の差

これが ADR 0014 の申し送り（Q-1 の品質面）に対する実測である。

| 構成 | 採点関数 | `recall@1` | `recall@5` | `recall@10` | `MRR` | micro |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| `pg-lexical-only-r5` | `ts_rank` | 0.2573 | 0.5444 | **0.6199** | **0.7359** | 126/236 = 0.534 |
| `sqlite-lexical-only-r5` | `bm25()` | 0.2565 | 0.5732 | **0.6494** | **0.7177** | 135/236 = 0.572 |
| 差（bm25 − ts_rank） | | −0.0008 | **+0.0288** | **+0.0295** | **−0.0182** | +9件 |

⚠️ **`recall@10` の +0.0295 は、`testdata/eval/README.md`「数字の読み方」が
「判断材料にしない」と定める ±2〜4ポイントの帯の中にある。** 総合値1本での優劣判定は禁止されているので、
以下のタグ別と per-query 差分を併せて読むこと。

🔑 **`recall@10` と `MRR` が逆を向いている。** `bm25()` は10件の枠内に多く入れているが、
最初の正解の位置は `ts_rank` のほうが上である。片方だけを引用すると逆の像になる。

### 🔴 長文優遇の切り分け（`data/README.md` の必須併記）

`bm25()` は文書長で正規化し、Postgres の `ts_rank` は**正規化フラグ 0 で測っているのでしない**。
この評価セットは長い一覧表チャンクを gold として繰り返し使うので、
出た差が「長文優遇の差」なのか「検索品質の差」なのかを切り分ける内訳を必ず併記する。

| 内訳 | `ts_rank` | `bm25()` |
| --- | ---: | ---: |
| gold ≤520字 | 101/180 = **0.561** | 110/180 = **0.611** |
| gold >520字 | 25/56 = **0.446** | 25/56 = **0.446** |
| 名指しの長文3件（`readme#005` / `requirements#023` / `requirements#008`） | 3/15 = 0.200 | 3/15 = 0.200 |

🔑 **`bm25()` の +9件は、すべて 520字以下のチャンクで起きている。** 520字超の gold は
**両者とも 25/56 で完全に同数**で、名指しの3件も 3/15 で同数だった
（内訳は入れ替わっている——`readme#005` が 2→1、`requirements#008` が 1→2）。

⇒ **「BM25 が長文を不利に扱ったぶん短文が浮いた」という形は、この 12本の測定には現れていない。**
長文側が減っていないので、増分を長さ正規化の効果として説明することはできない。
⚠️ ただし本測定は長さ正規化の有無を A/B したわけではない（`ts_rank` と `bm25()` は式そのものが違う）。
言えるのは「長文側の被害が観測されなかった」までである。

## 層3 — ハイブリッド：SQLite 側の `alpha` 掃引

Postgres の既定 `alpha = 0.8` は **ADR 0015 が Postgres の正規化条件で選んだ値**であり、
ADR 0017 は「SQLite にそのまま当てはめない」と申し送っている。そこで SQLite 側で掃引した。

| `alpha` | `recall@10` | `MRR` | micro |
| ---: | ---: | ---: | ---: |
| 0.0（語彙のみ） | 0.6494 | 0.7177 | 135/236 |
| 0.5 | 0.7040 | 0.7590 | 149/236 |
| 0.6 | 0.7140 | 0.7577 | 151/236 |
| 0.7 | 0.7218 | 0.7577 | 154/236 |
| 0.8 | 0.7245 | 0.8075 | 156/236 |
| **0.85** | 0.7338 | **0.8279** | 158/236 |
| **0.9** | **0.7438** | 0.8195 | **161/236** |
| 0.95 | 0.6830 | 0.7670 | 149/236 |
| 1.0（ベクトルのみ） | 0.5960 | 0.7055 | 131/236 |

**最大値 0.7438 は `alpha = 0.9`。** ADR 0015 と同じプラトー規約（最大値から −0.02 以内）を当てると
しきい値は 0.7238 で、**プラトーは 0.8〜0.9**（0.7 は 0.7218 で 0.0020 だけ外れる）。
0.95 で 0.6830 へ急落するのは Postgres 側の掃引と同じ形である。

⚠️ **0.85 と 0.95 は指示書の掃引点に無かったが追加した。** 指定された {0.5, 0.6, 0.7, 0.8, 0.9} だけでは
最大値が**掃引範囲の端**に来てしまい、プラトーが存在するのかどうかを読めなかったためである
（0.95 を測って初めて右端が確定し、0.85 を測って初めてプラトーの中に中心の測定点ができる）。

### Postgres の既定を SQLite にそのまま当てた場合

| 構成 | `recall@10` | `MRR` | micro |
| --- | ---: | ---: | ---: |
| `pg-hybrid-08-r5`（Postgres の既定） | 0.7241 | 0.8072 | 157/236 |
| `sqlite-hybrid-08-r5`（同じ `alpha` を当てた） | 0.7245 | 0.8075 | 156/236 |
| `sqlite-hybrid-09-r5`（SQLite のプラトー内・最大） | 0.7438 | 0.8195 | 161/236 |
| `sqlite-hybrid-085-r5`（SQLite のプラトー中心） | 0.7338 | **0.8279** | 158/236 |

🔑 **`alpha = 0.8` では両ストアの総合値がほぼ重なる**（`recall@10` の差 0.0004・`MRR` の差 0.0003）。
層2 で見た採点関数の差が、`alpha = 0.8`（語彙の重み 0.2）まで薄めると総合値の上では見えなくなっている。

⚠️ **これを「どちらでも同じ」と読まないこと。** 差が消えたのは総合値であって、
層2 の per-query 差分（12クエリが入れ替わった）が消えたわけではない。

⚠️ **SQLite 側のプラトーは 0.8〜0.9 で、Postgres の 0.7〜0.9 と一致していない。**
ADR 0017 の「そのまま当てはめない」という申し送りは、この形で数字になった。
どの値を採るかは本書の管轄外である。

## 層1 の latency 差＝「ストアの差」

層1 で品質が完全に一致したので、**純ベクトルの2本の差はストアの実装差だけを含む**。

| | 系統2 p50 | 系統2 p95 |
| --- | ---: | ---: |
| `pg-vector-only-r5` | **9.3** | **13.5** |
| `sqlite-vector-only-r5` | **93.7** | **207.7** |
| 比 | **約 10倍** | **約 15倍** |

コードの形の違いは次のとおり（**内訳は測っていない**。以下は「何をしているか」であって
「どこに何 ms 使ったか」ではない）。

- Postgres は `-(embedding <#> $2::vector)` を **1本の SQL の中**で計算する。距離計算は C の pgvector 拡張。
- SQLite は `WHERE org_id = ?` で候補行を返すだけで、**259行ぶんの 4096バイト BLOB を
  `database/sql` 経由で Go に運び**、Go で内積を取る（ADR 0017 Decision 2）。
  加えて SQLite エンジン自体が純 Go の VM（`modernc.org/sqlite`）である。

⚠️ **これは「SQLite が遅い」ではなく「この構成が遅い」である。** cgo なしという制約
（`CLAUDE.md` 地雷5）と、比較用という位置づけ（索引も持たない）を含んだ数字である。

## `alpha` は SQLite でも latency に効かない

Lane 4 が Postgres について観測した性質は、SQLite でも同じ形で成り立っている。
系統2 の p50 は `alpha` を 0.0 から 1.0 まで振っても **91.4〜95.4ms** の範囲に収まり、
`alpha = 0.0`（92.2）と `alpha = 1.0`（93.7）の差は 1.5ms で、掃引点どうしのばらつきと区別できない。

理由も同じで、実装にある。`searchRows` は `alpha` を見ずに

```go
candidates, err := s.candidates(ctx, q, vector)   // 全行のベクトルスコア
lexical,    err := s.lexicalScores(ctx, q, expression) // 語彙スコア
```

の**両方を必ず呼ぶ**。`alpha` は合成時の重みであって、語彙検索を止めるスイッチではない。

⇒ **両ストアとも `alpha` 掃引では語彙検索の追加コストを測れない。**
Postgres 側でそれを測るには語彙実装前のリビジョンとの統制測定が要り、それは
[`2026-09-02-eval-hybrid-latency.md`](2026-09-02-eval-hybrid-latency.md) が済ませている。
**SQLite 側の同等の統制測定は本書では行っていない**（SQLite ストアは語彙と同時に入ったので、
「語彙が無い SQLite ストア」というリビジョンが存在しない）。

## 要件定義 §8 の予算に対する位置

要件定義 §8 は **「1万チャンクに対し検索 p95 < 200ms（埋め込み往復を除く）」**。

| 構成（**259チャンク**） | 系統2 p95 | 予算 200ms に占める割合 |
| --- | ---: | ---: |
| `pg-hybrid-08-r5` | 14.4ms | 約 7% |
| `sqlite-hybrid-08-r5` | 203.5ms | **約 102%** |

🔴 **これは「SQLite が §8 を満たさない」という意味ではないし、「Postgres が満たした」という意味でもない。**
§8 は **1万チャンク**での要件で、本測定は **259チャンク**（要件の 2.6%）である。
⚠️ **この数字から 1万件を外挿しないこと**（固定費と可変費を分離していない。理由は Lane 4 の同名節に同じ）。
言えるのは「**259チャンクの時点で、比較用 SQLite の系統2 p95 は 1万チャンクの予算とほぼ同じ大きさである**」
という観察までである。

---

## この数字の限界

- **規模**: 259チャンク・**両ストアとも索引なしの全探索**。10万件では別の数字になる（Phase 1 項目7・ADR 0007）。
  SQLite 側は Go 側総当たりなので、規模に対する伸び方が Postgres と同じとは限らない
- **単一プロセス・WSL**: 評価ランナーは1本のプロセスから逐次にクエリを投げる。並行負荷は掛けていない。
  SQLite は同一ホストのファイル、Postgres は Docker のポート転送（5433）越しで、
  **経路そのものが違う**。系統2 の差にはその違いも含まれる
- **占有ベンチではない**: GPU は他アプリと共有。系統1 のばらつき（44〜390ms）はその反映
- **内訳を測っていない**: 層1 の 10倍差を「BLOB の転送」「純 Go の VM」「Go の内積」に分解していない。
  分解が要るならプロファイラの仕事である
- **語彙採点の比較は A/B ではない**: `ts_rank`（正規化 0）と `bm25()` は式そのものが違う。
  長さ正規化だけを入れ替えた比較ではない
- **コーパスの偏り**: ADR・規約文書で識別子が濃い（`pgvector`・`org_id`）。
  ここで出た `alpha` のプラトーを一般の日本語文書に外挿しないこと（`testdata/eval/README.md` の限界節）
- **`alpha` の掃引は SQLite 側だけ rounds=5**。Postgres 側の掃引は
  [`2026-09-02-eval-lexical-hybrid.md`](2026-09-02-eval-lexical-hybrid.md) §5 の **rounds=1** の測定である。
  品質指標は rounds に依存しない（Lane 4 が rounds=1 と rounds=5 の一致を確認済み）ので比較はできるが、
  **同じ測定ではない**

## 再現手順

```bash
docker compose up -d                      # PostgreSQL（sqlite の測定には不要）
set -a; . ./.env; set +a                  # RECALL_DATABASE_URL と RECALL_OLLAMA_URL が要る

# 層1・層2（Postgres 側の 1.0 と 0.8 は Lane 4 の JSON を再利用した）
make eval EVAL_LABEL=pg-lexical-only-r5     EVAL_STORE=postgres EVAL_ALPHA=0.0 EVAL_ROUNDS=5 GPU_NOTE="…"
make eval EVAL_LABEL=sqlite-vector-only-r5  EVAL_STORE=sqlite   EVAL_ALPHA=1.0 EVAL_ROUNDS=5 GPU_NOTE="…"
make eval EVAL_LABEL=sqlite-lexical-only-r5 EVAL_STORE=sqlite   EVAL_ALPHA=0.0 EVAL_ROUNDS=5 GPU_NOTE="…"

# 層3（掃引）
for a in 0.5 0.6 0.7 0.8 0.85 0.9 0.95; do
  make eval EVAL_LABEL=sqlite-hybrid-${a/0./0}-r5 EVAL_STORE=sqlite EVAL_ALPHA=$a EVAL_ROUNDS=5 GPU_NOTE="…"
done
```

⚠️ `make eval` は `make check` に含まれない（CI に Ollama も GPU も無く、評価は検査ではなく計測だから。ADR 0013）。

🔑 **`git_modified: false` で測ること。** 12本すべて作業木が clean な状態でビルドしている。
`EVAL_OUT` の既定は `docs/benchmarks/data/` なので、**前の測定の JSON が未追跡のまま残っていると
次のビルドが `git_modified: true` で刻まれる。** 本測定は `EVAL_OUT` をリポジトリ外へ向けて 12本を測り、
全部終えてから `docs/benchmarks/data/` へ移した。

🔑 **`EVAL_STORE=sqlite` の評価 DB（既定 `bin/recall_eval.db`）は毎回作り直される。**
`bin/` は gitignore 済みなので作業木は汚れない。

## レポートの読み方について気づいたこと（直していない）

- `conditions.alpha` は float32 を経由するので、`0.6` を渡したレポートに
  `0.6000000238418579` と刻まれる（`0.85` → `0.8500000238418579`・`0.9` → `0.8999999761581421`）。
  値としては正しいが、**JSON を機械で突き合わせるとき `== 0.6` が偽になる**。

- `conditions.ts_rank_normalization` と `rrf_k` は `store: sqlite` のレポートでも 0 / 60 が入る。

- `conditions.alpha_note` は `store` に関わらず「既定 0.8 は 2026-09-02 の評価セットで選んだ」という
  Postgres 由来の文言が入る。SQLite のレポートにもそのまま入るので、
  **SQLite で 0.8 が選ばれた形跡があるように読めてしまう**
