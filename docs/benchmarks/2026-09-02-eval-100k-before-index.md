### 3.1 系統1 と系統2 がほぼ同じ値になった

10万件では **系統2 の p95 が系統1 の p95 を上回っている構成がある**（ハイブリッド 5765.83 vs 5758.34）。

🔴 **これは矛盾ではないし、「埋め込み往復が負の時間だった」という意味でもない。**
2つの系統は別々の 290 サンプルの分布で、それぞれのパーセンタイルである。
259 件では両者が 74.57 と 14.45 に分かれていたのに対し、10万件では検索本体が 5〜6秒に伸び、
**Ollama への往復（259 件の測定で 40〜110ms の幅を作っていた成分）が分布の揺らぎに埋もれた。**

⚠️ ここでも引き算をしていない。言えるのは「系統1 の p95 が 5758.34ms、系統2 の p95 が 5765.83ms」
という2つの実測値だけである。

### 3.2 3本は同じモードにある

[`2026-09-02-eval-morph-vs-bigram.md`](2026-09-02-eval-morph-vs-bigram.md) §6 は、
同一条件の反復でも系統2 が**2つのモードに割れる**ことを記録している。本測定でも確認した。

`alpha` は latency に効かない（`ts_rank` は `alpha` の値に関わらず全行に計算される。
[latency 正本](2026-09-02-eval-hybrid-latency.md) §「語彙検索の追加コストは `alpha` では測れない」）ので、
**3本は latency については同一条件の3反復である。**

| ラベル | r1 | r2 | r3 | r4 | r5 | 全体 p50 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `100k-hybrid-08-r5` | 3841.1 | 3803.5 | 3817.3 | 3816.1 | 3850.3 | 3830.2 |
| `100k-vector-only-r5` | 3868.7 | 3861.9 | 3783.6 | 3794.7 | 3849.5 | 3820.8 |
| `100k-lexical-only-r5` | 3705.3 | 3720.8 | 3791.4 | 3726.0 | 3759.6 | 3740.7 |

ラウンド別の系統2 中央値（ms）。**3本 × 5ラウンド = 15点すべてが 3705〜3869ms に収まり、
最大と最小の開きは 4.4% である。** ⇒ **本測定にモードの割れは現れていない。**

⚠️ **「10万件ではモードが消える」とは言えない。** 分かるのは、259 件で 2倍に割れていた幅が、
5〜6秒という絶対値の前では見えなくなっているということだけである。

### 3.3 統制測定 — 259 件は本日 9.00ms、正本は 14.45ms

🔑 **同一セッション・同一バイナリで測った 259 件の系統2 p95 は 9.00ms** で、
既存の正本（別セッション・`b3f1a64`）の **14.45ms** ではない。
morph 文書の言うモードで見ると、統制は**低モード側**、正本は**高モード側**である。

⇒ **規模の倍率を1つの数字で書けない。**

| 基準 | 系統2 p95 | 100k / 259 の倍率 | データの倍率 |
| --- | ---: | ---: | ---: |
| 本日の統制（低モード） | 9.00 | **640.8x** | 387.1x |
| 既存の正本（高モード） | 14.45 | **399.0x** | 387.1x |

🔴 **どちらを分母にするかで「線形より速い」と「線形より遅い」が入れ替わる。**
本測定は原因（モードの正体）を特定していないので、**スケーリングの次数を主張しない。**

### 3.4 要件定義 §8 の予算に対する位置

要件定義 §8 の性能要件は **「1万チャンクに対し検索 p95 < 200ms（埋め込み往復を除く）」**。

🔴 **本測定は 100,259 チャンクで、要件が課された規模の 約10倍である。**
（[latency 正本](2026-09-02-eval-hybrid-latency.md) §要件定義 §8 が
「1万」と「10万」を混ぜるなと明記している。混ぜていない。）

| | 値 |
| --- | ---: |
| 既定構成の系統2 p95（**100,259チャンク**・実測） | **5,765.83ms** |
| §8 の予算（**1万チャンク**での要件） | 200ms |

**参考値（測っていない）**: 上の実測値を件数に比例させて 1万件相当へ縮めると
5765.83 ÷ 10.03 ≈ **575ms**。

🔴 **これは測定値ではない。** 単純な比例で割っただけで、次の理由から根拠が無い。

1. **固定費と可変費を分離していない。** §4 の `EXPLAIN` は、走査だけなら 12.8ms、
   距離計算を足すと 224ms、既定構成の SQL 全体では 2,172ms という**非比例な内訳**を示している
2. **10万件では中間結果が `work_mem` を溢れて一時ファイルに書かれる**（§4）。
   1万件でも溢れるかは測っていない
3. **10万件では並列度が変わりうる。** §4 のとおり既定構成の SQL は単一プロセスで走るが、
   件数が変われば planner の選択は変わりうる
4. §3.3 のとおり、259 → 100,259 の倍率自体が 399x とも 641x とも読める

⇒ **1万件の数字が要るなら、1万件で測ること。** 本書はそれを測っていない。

### 4.2 既定構成の SQL の計画

```
 Limit  (actual time=2223.136..2223.140 rows=10 loops=1)
   Buffers: shared hit=1815533 read=185421, temp read=16633 written=8493
   ->  Sort  (actual time=2223.134..2223.137 rows=10 loops=1)
         Sort Method: top-N heapsort  Memory: 39kB
         ->  WindowAgg  (actual time=699.554..2188.804 rows=100259 loops=1)
               ->  Seq Scan on chunks  (actual time=0.015..44.131 rows=100259 loops=1)
                     Filter: (org_id = 1)
                     Buffers: shared read=18529
 Planning Time: 0.853 ms
 Execution Time: 2223.386 ms
```

読み取れること:

1. 🔴 **`Seq Scan` である。** 索引は使われていない（使える索引が無い）。
   100,259 行すべてを読み、`Filter: (org_id = 1)` で 1行も落ちていない
2. 🔴 **並列化されていない。** 単一プロセスである（`Workers Launched` の行が無い）。
   窓関数 `MAX(lexical_score) OVER ()` を含む計画は parallel-safe にならない
3. 🔴 **一時ファイルへ溢れている。** `temp read=16633 written=8493` は 8KB ブロック単位なので、
   **書き 66MB・読み 130MB**。`work_mem` は 4MB（§1.3）で、`WindowAgg` が 100,259 行を
   溜める場所が無い
4. **走査そのものは 44ms**（`Seq Scan` の actual time）。残り 2,100ms 以上が
   `WindowAgg`（699.554 → 2188.804）と最終の top-N heapsort に費やされている

### 4.3 内訳の切り分け（同じデータ・同じセッション・各2回）

`Execution Time`（ms）。2回目の値を採る。

| 何を測ったか | 並列度 | 実行1 | 実行2 |
| --- | ---: | ---: | ---: |
| **既定構成の SQL（本番と同じ）** | 単一 | 2388.8 | **2172.0** |
| 窓関数を外した合成 + top-N（`MAX() OVER ()` なし） | 3プロセス | 598.0 | **591.9** |
| 両スコアを全行に計算して集計（並べ替え無し） | 3プロセス | 379.3 | **372.1** |
| ベクトル距離だけを全行に計算（集計） | 3プロセス | 215.5 | **224.4** |
| `ts_rank` だけを全行に計算（集計） | 単一 | 677.4 | **653.5** |
| 走査だけ（どちらのスコアも計算しない） | 単一 | 18.6 | **12.8** |

🔴 **この表を足し算・引き算で読まないこと。並列度が行ごとに違う。**
planner が選んだ計画をそのまま記録してあり、揃えていない。

- 「走査だけ」（12.8ms）は planner が `Aggregate` の下で `count(*)` を選んだ形で、
  **ヒープの全列を読んでいない**（§1.1 のとおり埋め込みは TOAST にある）
- `ts_rank` だけは planner が並列を選ばなかった。**224.4ms（3プロセス）と 653.5ms（単一）を
  「ベクトルより `ts_rank` が3倍重い」と読んではならない**

同じ計画の形で比べられるのは次の1組だけである。

| 同じ計画の形（3プロセス並列・1ワーカーあたり 33,420 行） | ワーカー内の `Partial Aggregate` 時間 |
| --- | ---: |
| ベクトル距離だけ | 215.9ms |
| ベクトル距離 + `ts_rank` の両方 | 362.6ms |

⇒ 同じ形の計画で、**両スコアの計算はベクトル距離だけより 1.68倍の時間がかかっている。**
（この 2つの差を「`ts_rank` のコスト」と名指ししない。同じノード内の別の式なので、
式の評価順や共通部分式の扱いを本測定は分離していない。）

🔑 **本測定で最も大きい単一の項は、距離計算でも `ts_rank` でもない。**
窓関数を外すだけで 2,172ms → 592ms になっている。⚠️ ただしこれは
**「窓関数のコストが 1,580ms」ではない**——窓関数を外すと計画が単一プロセスから
3プロセス並列に変わり、一時ファイルへの溢れも消えるので、**3つの変化が同時に起きている。**
本測定はそれを分離していない。

⚠️ この 50 秒がどのサンプルにどれだけ乗ったかは分離していない。

### 🔴 評価用 DB は他レーンと共有されている

⇒ **同じマシンで複数のレーンが `make eval` を走らせると、あとから走ったほうが先のデータを消す。**
10万件の投入は初回 23 分（以後キャッシュがあれば約1分）かかるので、この事故は安くない。

## 6. この数字の限界

- 🔴 **本書は before であって、索引の判断ではない。** HNSW / `GIN (lexemes)` を入れる判断は
  ADR 0007 手順 3 の仕事である。**本書は結論を書いていない**
- **紛れ込みの分布が評価セットと違う。** 評価セットは ADR・規約文書で
  `pgvector` / `org_id` / `CNF-001` のような ASCII 識別子が濃い。紛れ込みは素の日本語 Wikipedia で、
  平均文字数は短いのにレキシームは多い（§1.1）。⇒ **「10万件の実文書」一般の話に一般化しないこと**
- **`recall` の希釈は紛れ込みの選び方に依存する。** 無関係な文書10万件を足せば正解は押し出されるが、
  どれだけ押し出されるかは「無関係さ」の程度で変わる。ADR 0019 が Wikipedia を選んだ理由は
  再現性であって、「実運用のコーパスに似ているから」ではない
- **58クエリ・タグ n=6〜8。** 総合 `recall@10` は1クエリで 0.017、タグ別は1クエリで 0.13〜0.17 動く。
  §2.2 で「差」と呼べるのは4タグだけである
- **単一プロセス・WSL・共有 GPU。** 占有ベンチではない。系統1 のばらつきは GPU 共有の反映で、
  `100k-vector-only` の計測中には他レーンの `make check` が約 50 秒走っている（§5）
- **PostgreSQL は既定設定。** `work_mem` 4MB・`shared_buffers` 128MB・
  `max_parallel_workers_per_gather` 2（§1.3）。**チューニングしていない**ので、
  §4 の一時ファイル溢れと並列度は、この設定に条件付きの観察である
- **`EXPLAIN` は 1クエリ1本。** `q-014` はクエリ長 16文字・bigram 15トークンで、
  `ts_rank` のコストはクエリのトークン数に依存する。**他のクエリでは内訳の比が変わりうる**
- **259 件の比較対象が 2つある。** 本日の統制（系統2 p95 9.00ms）と既存の正本（14.45ms）で、
  どちらを分母にするかで倍率が 641x と 399x に割れる（§3.3）。
  🔴 **本測定はスケーリングの次数を主張しない**
- **1万件は測っていない**（§3.4）。要件定義 §8 の規模での数字が要るなら、その規模で測ること

🔴 **他のレーンと `make eval` を同時に走らせないこと**（§5 の最後）。
`recall_eval` は共有で、あとから走ったほうが 10万件を消す。
