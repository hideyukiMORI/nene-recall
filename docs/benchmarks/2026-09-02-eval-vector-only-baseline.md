ADR 0009 が Phase 1 の必須要件と定めた検索品質の評価。**語彙検索を実装する前の基準線**であり、
以後の Q-1（tsvector か BM25 か）・Q-2（bigram か形態素か）・Q-3（`alpha` の最適値）の判断は、
すべてこの数値との差分で行う。

生データ: [`data/2026-09-02-eval-baseline.json`](data/2026-09-02-eval-baseline.json)
（**集計値はすべて per-query の生データから第三者が再計算できる**）

### 🔑 評価セットは判別力を持っている

`README.md` の自己点検条項「`recall@10` が 0.95 を超えたら測定器の故障を疑う」に対し、
実測は **0.596**。**改善の余地が約4割**あり、語彙検索・ハイブリッド合成・reranker の
効果を測れる状態にある。満点に近い評価セットは何も語れないので、この値は健全である。

`MRR = 0.705` は「最初の1件はだいたい1〜2位に来る」ことを意味する。
つまり**上位1件の妥当性は高いが、関連チャンクを網羅的に集める力が弱い**。
引用付きで答えるという用途（要件定義 §2.1）では後者が効く。

### 🔴 事前の予想と逆の並びになった

評価セット作成時の予想は「ベクトルは `paraphrase` / `synonym` / `orthography` に強く、
`exact-term` / `numeric` / `negation` に弱い」だった。**実測はほぼ逆である。**

- 弱いと予想した `negation`（0.72）と `numeric`（0.70）が**上位2つ**
- 強いと予想した `paraphrase`（0.44）と `synonym`（0.47）が**下位2つ**

読み方: このコーパスでは、`numeric` / `negation` のクエリも本文の語をそのまま含みがちで、
bge-m3 はその**字面の一致に十分反応している**。逆に `paraphrase` / `synonym` は設計上
本文の語彙を避けて作ってあるため、埋め込みに意味の橋渡しを要求する。
**bge-m3 はその橋渡しを、期待されていたほどは行っていない。**

⚠️ **ただしこれは仮説であって結論ではない。** 各タグ n=6〜8 なので、1クエリの成否で
recall は約 0.14 動く。`paraphrase` 0.44 と `negation` 0.72 の差（0.28）は1クエリ分の
ゆらぎより大きいが、**総合値1本での優劣判定を禁じる**（`testdata/eval/README.md`）規則は
タグ別にも適用される。次の判断材料にはするが、根拠として引用するときはこの注記ごと引くこと。

### ⚠️ 戦略への含意（要検証）

語彙検索（項目4）が埋められるのは主に `exact-term` の取りこぼしだが、
**最大の穴である `paraphrase` 0.44 は語彙検索では埋まらない**。字面が違うことが
そのカテゴリの定義だからである。もしこの傾向が語彙検索実装後も残るなら、
Q-1/Q-2 の選択よりも**埋め込みモデルの選択か reranker（Q-4）のほうが効く**可能性がある。
Q-4 は「Phase 1 は入れない」と決めてあるが、**その判断はこの数字を見る前のものである**。

## 🔑 この結論は注釈の修正に耐えた

基準線は**2回測っている**。1回目は第一注釈者だけが作った評価セット（56クエリ・222注釈）に対して、
2回目は**第二注釈者との突き合わせで見つかった誤りを直した後**（58クエリ・236注釈）に対して。

| | 修正前 | 修正後 |
| --- | ---: | ---: |
| `recall@10` | 0.605 | 0.596 |
| `MRR` | 0.730 | 0.705 |
| 最下位タグ | `paraphrase` 0.44 | **`paraphrase` 0.44** |
| 最上位タグ | `negation` 0.77 | **`negation` 0.72** |

⚠️ **2つの数値は同じ評価セットに対するものではない**ので、差分そのものに意味は無い
（`queries.jsonl` の sha256 が違う。README の比較規約どおり）。意味があるのは次の事実である:

> **10クエリの注釈を直し、2クエリを新規に足しても、タグの順位はほぼ動かなかった。**

修正は無視できる規模ではなかった（`q-040` に3件追加・`q-019`/`q-020` は方針を逆向きに正して
入れ替え・`q-038` から1件除外）。それでも `paraphrase` が最下位で `negation` が最上位という
並びは保たれた。⇒ **「予想と逆」という結論は、少なくとも注釈の誤りという要因では説明できない。**

これは結論を強めるが、証明はしない。**注釈者2人は同じモデル**であり（`testdata/eval/README.md`
の限界節を参照）、共有された盲点はこの方法では検出できない。

## 注釈の検証で分かったこと（Q-1 への申し送り）

第二注釈者との突き合わせ（Jaccard 0.874・クエリ単位の完全一致 34/56）で、
**Q-1 の判断を歪めうる構造が2つ**見つかっている。語彙検索に着手する人は必ず読むこと。

1. **`orthography` の gold からキーワードの濃い行が系統的に落ちていた。** 修正済みだが、
   同種の取り漏らしは**語彙手法に不利な方向にだけ**効くバイアスである
2. **長い一覧表チャンクが gold として繰り返し使われている**（`readme#005` は1,136字で5クエリの正解）。
   **BM25 は文書長で正規化し、Postgres の `tsvector` ランキングは既定でそうしない。**
   ⇒ **Q-1 のレポートには gold の長文チャンク依存度を必ず併記すること。**
   そうしないと、長文優遇の差なのか検索品質の差なのかを切り分けられない

また、`exact-term` には**構造的な天井**がある。`q-007`（`PdoChunkSearchRepository.php`）の gold は
クエリのリテラル全体を本文に含まないため、**完全な語彙一致器でも `recall@10` は 5/7 = 0.714 が上限**。
これは注釈の誤りではなくコーパスの事実なので gold は残してある。相対比較は無傷だが、
**`exact-term` の絶対値を語彙一致器の性能と読まないこと。**

## 数字の読み方（`testdata/eval/README.md` の規則を再掲）

- 58クエリなので、1クエリの成否で総合 recall は約 **0.017** 動く。**±0.02〜0.04 の差は判断材料にしない**
- タグ別は n=6〜8 なので1クエリで約 **0.14** 動く。カテゴリ単位で複数クエリが動く変化だけを見る
- 判断に使ってよいのは (a) 大差 (b) カテゴリ別の一貫した傾向 (c) per-query の差分リスト
- `p95` は 280 サンプル。GPU の占有状況で揺れる

## 規模の限界

このコーパスは 259 チャンクで、要件定義 §8 の「1万チャンクに対し p95 < 200ms」の
検証には**ならない**。`p95`（埋め込み除く）3.3ms は「索引なし全探索・259チャンク時点」の値であり、
規模の性能検証と HNSW の判断は Phase 1 項目7 の仕事である（ADR 0007）。

また、コーパスは ADR・規約文書であり `pgvector`・`HNSW`・`org_id` のような識別子が濃い。
**一般の日本語文書に外挿しないこと。**

## 追記2: §5 の「6桁丸め」仮説は否定された（2026-09-02）

`nene-origin` 側（ベンチ §5 を書いた担当）から、ずれの原因として
「pgvector 上で `1 - (e <=> qv)` を使い、**ベクトルを SQL リテラルへ 6桁で丸めて**流し込んでいた」
という申告があった。**もっともらしいので実測で確かめたところ、否定された。**

| 丸め | 類似度 |
| --- | --- |
| 丸めなし | 0.5899 / 0.5165 / 0.3440 / 0.2804 |
| **6桁** | **0.5899 / 0.5165 / 0.3440 / 0.2804**（1桁も動かない） |
| 4桁 | 0.5898 / 0.5164 / 0.3440 / 0.2804 |
| 3桁 | 0.5899 / 0.5162 / 0.3439 / 0.2809 |
| 2桁 | 0.5870 / 0.5156 / 0.3402 / 0.2779 |
| §5 の記録 | 0.5738 / 0.5054 / 0.3182 / 0.2685 |

**2桁まで潰しても記録値には届かない。** 1024次元の正規化済みベクトルでは、成分あたりの丸め誤差が
内積の総和の中で相殺されるため、6桁丸めがコサインに与える影響は 1e-6 の水準にとどまる。

⇒ **原因は特定された（下記「追記3」）。**

🔑 **もっともらしい説明を、測らずに採用しないこと。** 丸めは原因として自然に聞こえるが、
実測は「1桁も動かない」と答えた。ここで納得して閉じていたら、**間違った原因が正本に残り、
本当の原因は二度と探されなかった。**

## 追記3: 原因は末尾の「。」だった — 決着（2026-09-02）

`nene-origin` 側が「§5 の表は `psql` の出力を貼ったもので、実際に投入した本文とは違う」と
申告してきたので、実測で確かめた。**そのとおりだった。**

| 入力 | 類似度 |
| --- | --- |
| **全文（末尾の「。」あり）** | **0.5738 / 0.5054 / 0.3182 / 0.2685** ← **§5 の記録値と4件とも完全一致** |
| §5 の表のまま（「。」なし） | 0.5899 / 0.5165 / 0.3440 / 0.2804 ← 追記1で再現した値 |
| 34字で切り詰めた形 | 0.5852 / 0.5427 / 0.3182 / 0.2685 ← どちらとも一致しない |

⚠️ **申告された機構（34字での切り詰め）は原因ではない。** その形では記録値を再現しない。
**再現するのは「末尾の句点が落ちている」ことだけ**で、§5 の表は4文すべてから「。」が欠けていた。

### 結論

- **§5 の数字は正しかった。** 全文で正確に再現する
- **文書が間違っていた。** §5 は「入力」を書いたつもりで「**出力**」を書いていた

⇒ 追記1の結論「**§5 の絶対値は文書に書かれた手順から再現できない**」は正しく、
理由は「計算式を書いていない」ではなく「**入力を書いていない**」だった。

### 🔑 副産物: 末尾の句点1文字がコサイン類似度を 0.016 動かす

`0.5899 → 0.5738`。**1文字で、`recall@10` の判断に使うゆらぎ（0.017）と同じ桁が動く**〔実測〕。

⇒ **チャンク分割で末尾の句読点を落とすかどうかは、検索品質に効く実装判断である。**
取り込み側と評価セット側で扱いが違うと、原因の分からないスコア差になる。
`testdata/eval/corpus.jsonl` は句点を保持している（凍結済み）。

### 🔑 教訓

**もっともらしい説明を、測らずに採用しない。** これは2回効いた。

1. 「6桁丸め」仮説 — もっともらしかったが**1桁も動かなかった**（追記2）
2. 「34字での切り詰め」— 原因の方向は正しかったが**機構は違った**

⇒ 1回目で閉じていれば本当の欠陥は見つからず、2回目をそのまま採録していれば
**正しい結論に間違った機構が添えられた**まま残っていた。**方向が合っている説明ほど、
機構まで確かめずに通り抜けやすい。**
