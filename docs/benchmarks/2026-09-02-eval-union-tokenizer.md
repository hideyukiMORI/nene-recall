## 0. 追加で測った3本（指示からの逸脱）

指示の計測表は 9本（union 5・対照 4）だった。**`bigram` / `kagome` / `union` を `alpha=0.8` でもう1本ずつ、計3本を追加した。**
理由は2つある。

1. **latency の 2モード問題**（[`2026-09-02-eval-morph-vs-bigram.md`](2026-09-02-eval-morph-vs-bigram.md) §6）に対して、
   対照が各1本では**どちらのモードで出たのかを判定できない**。bigram / kagome の反復数を 2本ずつに増やした
2. `tsvector` の実バイト数は評価用 DB を直接見るしかないが、**`recall_eval` は `make eval` が毎回 DROP して作り直す**。
   分割器ごとに「実行 → 直後に SQL」の順で測る必要があり、追加の実行が要る

追加分は品質を1つも動かしていない（決定的であることの再確認）:

| 対 | `recall@10` 一致 | `MRR` 一致 | 上位10件の並びが違うクエリ |
| --- | --- | --- | ---: |
| `bigram-hybrid-08-r5-s3` vs `-rep2` | ✅ | ✅ | **0 / 58** |
| `kagome-hybrid-08-r5-s3` vs `-rep2` | ✅ | ✅ | **0 / 58** |
| `union-hybrid-08-r5` vs `-rep2` | ✅ | ✅ | **0 / 58** |

もう一点、**`alpha` の掃引点が bigram / kagome より粗い**（指示どおり 0.7 / 0.8 / 0.85 / 0.9 の4点）。
0.5 / 0.6 / 0.95 は測っていない。プラトーの読み方は §5 に但し書きがある。

### `paraphrase` が bigram を下回った経路の観察

**union のクエリ側トークンは平均 19.0 個で、その 71.6%（13.6 個）が bigram のトークンである**（58クエリ全体の実測）。
`ts_rank` は IDF を持たないので、**OR で並ぶ語の多数派が bigram 側になる。**

| クエリ | tag | bigram | kagome | union のトークン数（うち kagome 側が bigram と同一） |
| --- | --- | --- | --- | ---: |
| `q-055` `速いと言うために何が必要か` | `paraphrase` | `速い いと と言 言う うた ため めに に何 何が が必 必要 要か`（12） | `速い 言う ため 何 必要`（5） | 17（4） |
| `q-052` `良い数字が出たときに疑うべきこと` | `paraphrase` | 15 個 | `良い 数字 出る とき 疑う こと`（6） | 21（5） |
| `q-053` `後から他人が数字を…残すのか` | `paraphrase` | 27 個 | `後 他人 数字 確かめる られる よう する 何 残す の`（10） | 37（5） |

`q-055` の語彙スコアを3分割器で並べると経路が見える（`*` が gold）。

| 分割器 | 上位10件（`lexical_score`） |
| --- | --- |
| bigram | `adr-0005#004`(.0215) `coding-rules#036`(.0203) … gold **0件** |
| kagome | `adr-0011#005`(.0274) … `*adr-0011#007`(.0165) `*adr-0011#010`(.0165) ← **9・10位に gold 2件** |
| union | `coding-rules#036`(.0210) `adr-0005#004`(.0207) … `adr-0011#005`(.0113) ← **gold 0件**。kagome が9位に置いた `adr-0011#007` は圏外 |

kagome では gold が 9・10位に**ぎりぎり**入っていた（0.0165 vs 非 gold 0.0243）。
union ではその 0.0165 相当の寄与に bigram 側の加点が重なった結果、**上位が bigram の並びに戻り、gold は 10位の外へ出た。**

⚠️ **これは1クエリの観察であって、`paraphrase` の退行の説明ではない。**
`paraphrase` の −0.0442（対 bigram）の実体は **gold 2件**（micro 11/29 → 9/29）で、落ちたのは `q-051` と `q-053` である
（§6 の「union が両方を下回ったクエリ」と同じ2件）。`q-055` はそのどちらでもない——bigram でも union でも gold 0件で、
**bigram との差には寄与していない。** ここで `q-055` を並べたのは、kagome の利得が union で消える形が最も見やすいからである。

### `tsvector` の実バイト（予想「約 1.5 倍」の確認）

評価用 DB を分割器ごとに直接見た値である（`recall_eval` は `make eval` が毎回作り直すので、実行の直後に測った）。

```sql
SELECT tokenizer_id, count(*) AS chunks,
       round(avg(length(lexemes))::numeric,1) AS avg_lexemes,
       min(length(lexemes)) AS min_lexemes, max(length(lexemes)) AS max_lexemes,
       round(avg(octet_length(lexemes::text))::numeric,0) AS avg_tsvector_bytes,
       round(avg(length(lexeme_text))::numeric,0) AS avg_lexeme_text_chars
FROM chunks GROUP BY tokenizer_id;
```

| `tokenizer_id` | chunks | 平均レキシーム数 | 最小 | 最大 | 平均 `tsvector` バイト | 平均 `lexeme_text` 文字数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `bigram:nfkc-lower:v1` | 259 | 111.1 | 6 | 313 | 1414 | 446 |
| `kagome:ipadic:ascii-words:v1` | 259 | 53.5 | 3 | 135 | 694 | 269 |
| **`union:bigram+kagome:v1`** | 259 | **125.1** | 7 | 351 | **1817** | **716** |

| 量 | bigram → union |
| --- | ---: |
| `lexeme_text` の文字数（＝保存するトークン列そのもの） | **1.61 倍**（446 → 716。446 + 269 = 715 とほぼ一致し、連結が素通しであることを裏付ける） |
| `tsvector` の実バイト | **1.29 倍**（1414 → 1817） |
| 相異なるレキシーム数 | **1.13 倍**（111.1 → 125.1） |

🔑 **相異なるレキシーム数が 111.1 + 53.5 = 164.6 ではなく 125.1 である。**
`avg` は線形なので、**チャンクあたり平均 39.5 個のレキシームが両分割器で共通**（＝ kagome のレキシームの **73.8%** が
bigram のレキシーム集合に既に含まれる）ということになる。日本語の2文字語（`検索`・`演算` など）は
bigram のトークンとしても形態素としても同じ文字列になり、`to_tsvector` が重複を畳む。

⚠️ `length(tsvector)` は**相異なるレキシームの数**であって、生成したトークンの総数ではない。
`lexeme_text` の文字数（1.61倍）と `tsvector` の実バイト（1.29倍）が食い違うのはこのためである。
予想の「約 1.5 倍」がどちらの量を指していたかは予想文書からは決まらない。

## 9. この数字の限界

- **`union` の利得・退行はいずれも 1クエリ（0.017）前後である。** 総合値で bigram / kagome と分離しているものは1つも無い。
  1クエリを超えて動いたのは **`paraphrase` の語彙のみ −0.0442（対 bigram・gold 2件）と ハイブリッド +0.1156（対 bigram・gold 3件）**だけで、
  タグ n=7 では 1クエリで 0.14 動く粒度である
- **モードの原因は依然として不明**（§8・ADR 0021 Consequences 追従2）。同一バイナリ・同一データ・連続実行で系統2 が約2倍に割れる。
  本測定も原因を切り分けていないので、**latency の絶対値をここから外挿しないこと**。
  さらに**モードのラベルはセッション内でしか意味を持たない**ことが本測定で分かった（本日の kagome の「低」は前回の「高」と重なる）
- **kagome の高モードが1本も出なかった**ので、union と kagome の高モード同士の比較ができていない
- **規模**: 259チャンク・**索引なしの全探索**（ベクトルも `lexemes` も）。
  union は `tsvector` が bigram の 1.29倍・kagome の 2.62倍になるので、**GIN 索引を入れた構成では効き方が変わりうる**
- **58クエリ・タグ n=6〜8**。`testdata/eval/README.md`「数字の読み方」が総合値1本での優劣判定を禁じている
- **コーパスの偏り**: ADR・規約文書で識別子が濃い。`orthography` タグのクエリは `ハイブリット` / `ポスグレ` のように
  わざと表記を崩したもので、**形態素解析器にとっては未知語**である。一般の表記ゆれの話に一般化しないこと
- **`ts_rank` の重複の扱いを直接は測っていない。** union は重複を除かない設計（`internal/lexical/union` のコメント）だが、
  `to_tsvector` が `lexemes` 上で重複を畳むため、**二重加点は「同じレキシームが2回」ではなく「位置情報が2箇所」として効く**。
  本測定は per-query の順位変化を記録しただけで、この機構を分離していない
- **重複を除く v2・順序を変えた版・kagome の表層形版は測っていない**
- **占有ベンチではない**: GPU は他アプリと共有（測定中 4,823〜5,827 MiB・Util 8〜95%）。系統1 のばらつきはその反映

## 10. 再現手順

```bash
docker compose up -d
set -a; . ./.env; set +a
for a in 0 0.7 0.8 0.85 0.9; do
  make eval EVAL_LABEL=union-$a EVAL_ALPHA=$a EVAL_ROUNDS=5 \
       EVAL_TOKENIZER=union GPU_NOTE="占有状況を書く"
done
# 対照（同一セッションで測ること。別セッションの正本と latency を並べない）
make eval EVAL_LABEL=bigram-ctl EVAL_ALPHA=0.8 EVAL_ROUNDS=5 EVAL_TOKENIZER=bigram GPU_NOTE="…"
make eval EVAL_LABEL=kagome-ctl EVAL_ALPHA=0.8 EVAL_ROUNDS=5 EVAL_TOKENIZER=kagome GPU_NOTE="…"
```

⚠️ `make eval` は `make check` に含まれない（CI に Ollama が無く、評価は検査ではなく計測だから。ADR 0013）。

🔑 **`git_modified: false` で測ること。** `make eval` の既定の出力先が `docs/benchmarks/data/` なので、
**前の測定の JSON が未追跡のまま残っていると次のビルドが `git_modified: true` で刻まれる。**
本測定は 12本すべて `EVAL_OUT` をリポジトリ外へ向けて走らせ、全部終わってから `data/` へ移した。

🔑 **`tsvector` を測るなら、その分割器の `make eval` の直後に打つこと。** `recall_eval` は毎回 DROP される。

🔑 **latency を読むなら、片方だけ別セッションの値を使わないこと**（§8）。**モードのラベルもセッションをまたいで持ち越さないこと。**
