実装する**前**に、実装担当が予想を登録したものであり、`make eval` は1回も実行していない。

🔴 **この文書は測定後に書き換えない。** 外れていたら、外れたことが記録として価値を持つ。

## なぜ事前登録するか

測ってから「そう思っていた」と言えてしまうと、予想は何も検証しない。
基準線（[`2026-09-02-eval-vector-only-baseline.md`](2026-09-02-eval-vector-only-baseline.md)）は
まさにこの形で価値を出した——「ベクトルは `paraphrase` に強い」という**評価セット作成時の予想が
記録されていた**ので、実測がほぼ逆だったことが結論になった。予想が残っていなければ、
同じ数字はただの数字で終わっていた。

同じ手続きを Q-1（`tsvector` か BM25 か）・Q-2（bigram か形態素か）・Q-3（`alpha` の最適値）にも適用する。

## 測定の担当分離（この予想が持つ意味の source）

実装担当（この文書の書き手）は `make eval` を実行しない。測定はコーディネーターが行う。
実装した本人がスコアを見ると、無意識に「数字が良くなる方向」へ実装を寄せる余地が生まれるためで、
評価セットを起案したリナに `make eval` を禁じたのと同じ理由である。

⇒ **この予想は、結果を1つも見ていない状態で書かれている。**

## 実装者の補足予想

上の表とは別に、**実装した分割器の性質から導かれる、より細かく・より外れやすい予想**を登録する。
こちらは根拠が実装の中身にあるので、外れたときに「どの前提が誤りだったか」を特定できる。

### 総合値

| 指標 | 基準線 | 実装者の予想 | 幅 |
| --- | ---: | ---: | --- |
| `recall@10` | 0.596 | **0.63 前後** | 0.60〜0.68 |
| `MRR` | 0.705 | **0.75 前後** | 0.71〜0.80 |
| 1件も拾えなかったクエリ | 7 | **4〜5** | — |

`recall@10` の上げ幅を +0.03〜0.04 と小さく見るのは、語彙で救えるクエリが
**全滅7件のうち2〜3件に偏っている**と読むためである。58クエリの総合値は1クエリで 0.017 しか
動かないので、2〜3件の救済は総合で +0.02〜0.05 にしかならない。
⇒ **総合値は「±0.02〜0.04 は判断材料にしない」という規約の帯とほぼ同じ幅でしか動かない。**
これは失敗の予想ではなく、**総合値では Q-1 を決められない**という予想である。

### 🔴 `q-057` / `q-058` の撃ち分けは改善しない（登録分と食い違う予想）

コーディネーター登録分は「bigram は隣接情報を持つので `q-057`/`q-058` の撃ち分けだけは
改善しうる」としている。**実装者は改善しないと予想する。**

理由は実装の分割規則にある。この分割器は **CJK 連続部の内側でだけ bigram を作り、
英数トークンと CJK の境界を跨ぐ bigram は作らない**。

```
q-057 "Recall が落ちたら Corpus は動き続けるか"
q-058 "Corpus が落ちたら Recall は動き続けるか"
```

どちらも
- 英数トークン: `recall`, `corpus`（**集合として同一**）
- CJK 連続部: `が落ちたら` → `が落 落ち ちた たら` ／ `は動き続けるか` → `は動 動き き続 続け ける るか`（**同一**）

⇒ **2つのクエリのトークン集合は完全に一致する。** 語彙スコアは両クエリで同じ値になり、
順位差は最後までベクトル側だけが作る。したがって語彙を足しても撃ち分けは1ミリも改善しない。

**これが外れる（改善する）としたら**、原因は語彙側ではなく、合成で順位が動いた副作用である。
その場合「bigram が語順を捉えた」と読んではならない——**トークン集合が同一である以上、
語彙側にその情報は存在しない**。

この予想は、Q-2（bigram か形態素か）に直接効く。**形態素解析を入れても、
語と語の隣接を索引に持たない限りこの対は撃ち分けられない。** 撃ち分けが要るなら
必要なのは形態素ではなく**語のフレーズ索引（隣接）**である、というのが実装者の読みである。

### 🔴 `ts_rank` には IDF が無い（Q-1 の本丸はここだと予想する）

`ts_rank` は文書内の**出現頻度と位置**からスコアを作る関数で、
**コーパス全体での語の希少さ（IDF）を一切見ない**。BM25 との最大の差はここであり、
文書長正規化（`2` フラグ）は選べても IDF は選べない。

帰結として次を予想する。

1. **CJK bigram のうち高頻度なもの（`する`・`ため`・`こと`・`の◯` 等）が、
   希少な bigram と同じ重みで効く。** 長い日本語クエリほど、内容を持たない bigram が
   スコアの大半を占める
2. ⇒ **語彙スコアは「クエリと字面が重なる量」ではなく「ありふれた bigram をどれだけ含むか」に
   引っ張られる。** これは `paraphrase`/`synonym` を助けないだけでなく、`negation` のような
   既に取れているタグを**下げる**方向に働きうる
3. ⇒ **Q-1 の争点は「`tsvector` か BM25 か」という実装の選択ではなく、
   「IDF を持つか持たないか」である**と予想する

⚠️ この予想は測っていない。Q-1 の結論を先取りするものではなく、
**測定でこの機序が見えるかどうかを事前に宣言しておく**ためのものである。

### `alpha`（Q-3）

| 予想 | 根拠 |
| --- | --- |
| 最適 `alpha` は **0.7〜0.9 の側**に来る（＝ベクトル寄り） | 基準線でベクトルが `numeric`・`negation` で 0.7 台を出しており、語彙が救えるのは主に `exact-term` の数件。語彙を重くすると IDF の無いスコアの雑音が全タグに乗る |
| `alpha = 0.0`（純語彙）は基準線を**大きく下回る** | `paraphrase`・`synonym`・`negation` が総崩れになる |
| `alpha` の**掃引曲線は平坦**で、最適値の周りで 0.02 以内に収まる区間が広い | 58クエリの分解能（1クエリ = 0.017）では鋭い最適点は見えない |

🔴 **したがって「掃引して最も高かった値」を最適値として採らないこと。**
平坦なら、それは「決まらなかった」という結果である。0.7 に根拠が無いという現状
（CLAUDE.md 地雷7・要件定義 Q-3）は、掃引しただけでは解消しない。

## この予想が外れたときに疑うもの（順序も事前に決めておく）

1. **`lexeme_text` と `to_tsvector` の往復同一性**——Go の分割出力と DB 内のレキシームがずれていないか
   （往復同一性テストで縛ってあるが、テストが見ている範囲の外かもしれない）
2. **`ts_rank` の正規化フラグ**——C1 (`2|32`) と C2 の差
3. **`alpha`**——合成の重みが語彙側を潰している／持ち上げすぎている
4. **分割規則**——CJK/英数の境界の扱い、単独 CJK 文字の扱い
5. **評価セットの性質**——`README.md` の「既知の性質」（長文チャンク依存・`q-007` の天井）

🔴 **この順序で疑う。** 「予想が外れた」ときに最初に分割規則を疑うと、
数字が良くなる方向へ分割器を寄せる作業になり、それは評価セットの禁止事項
（スコアを見て入力を調整する）の実装側での再演になる。
**まず「測っているものが思っているものか」を疑う。**
