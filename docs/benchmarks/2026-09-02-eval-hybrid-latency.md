# 評価 2026-09-02 — ハイブリッド既定構成の latency 正本（rounds=5）

ADR 0015 で既定に決めた構成（加重和・クエリ内正規化・`alpha = 0.8`・bigram・`ts_rank` 正規化 0）の
**latency の正本**。[`2026-09-02-eval-lexical-hybrid.md`](2026-09-02-eval-lexical-hybrid.md) の測定は
rounds=1 で、同文書 §7 が「決定した構成で rounds=5 の正本を取り直すこと」と申し送っていた。本書がそれである。

**品質指標（`recall@k` / `MRR`）は rounds=1 の値と完全に一致した**ので、本書が新しく確定させるのは
latency だけである。

## 結果 — p50 / p95 を 2系統 × 2構成

🔴 **2系統は別々に実測した値である。引き算で出していない**（`CLAUDE.md` 地雷10）。
`SearchVector` で系統2 を直接測っており、`p95(除く)` は `p95(含む) − p95(埋め込み)` ではない。

| 構成 | 系統 | min | **p50** | **p95** | max |
| --- | --- | ---: | ---: | ---: | ---: |
| **ハイブリッド `alpha=0.8`** | 埋め込み往復を**含む** | 44.4 | **60.2** | **74.6** | 109.3 |
| **ハイブリッド `alpha=0.8`** | 埋め込み往復を**除く** | 4.0 | **9.3** | **14.4** | 19.5 |
| `alpha=1.0` | 埋め込み往復を**含む** | 48.1 | **60.1** | **72.7** | 79.9 |
| `alpha=1.0` | 埋め込み往復を**除く** | 3.9 | **9.3** | **13.5** | 16.4 |

単位は ms。各セル 290サンプル。

## 🔴 「語彙検索の追加コスト」は `alpha` では測れない

上の表で `alpha=0.8` と `alpha=1.0` の系統2 は **p50 が 9.268 と 9.264（差 0.004ms）** で、
実質的に同一である。**これは「語彙検索がタダ」という意味ではない。**

理由は SQL にある。`searchWeightedSumSQL` は `alpha` の値に関わらず
`ts_rank(lexemes, to_tsquery('simple', $6), $7)` を**常に全行に対して計算する**。
`alpha` は計算した語彙スコアに掛ける**重み**であって、語彙検索を止めるスイッチではない。

> ```sql
> -(embedding <#> $2::vector)                            AS vector_score,
> ts_rank(lexemes, to_tsquery('simple', $6), $7)         AS lexical_score
> ```
> `alpha = 1.0` は合成時に `(1 - alpha) = 0` を掛けるだけで、上の2行はどちらも実行される。

⇒ **`alpha` 掃引では語彙検索の追加コストは測れない。** これは実装の欠陥ではなく、
`alpha = 1.0` が純ベクトルと**順位で一致することを検証可能にする**ための設計である
（`searcher.go` の注記）。分岐を入れて条件付きで語彙を飛ばすと、その検証が「たまたま一致した」
のか「同じ経路を通ったから一致した」のか区別できなくなる。

### 統制測定 — 追加コストはリビジョン間でしか測れない

そこで**語彙検索が存在しないリビジョン `742119a`**（基準線を測ったコード）の
`cmd/eval` をビルドし、**同じセッション・同じマシン・同じ評価セット（sha256 一致）・同じ
rounds=5＋ウォームアップ1周**で測り直した。差し引きたい変数は「コード」だけである。

| リビジョン | 語彙検索 | 系統2 p50 | 系統2 p95 |
| --- | --- | ---: | ---: |
| `742119a`（統制） | **無し** | **2.22** | **2.88** |
| `b3f1a64` `alpha=1.0` | 有り（重み 0） | 9.26 | 13.47 |
| `b3f1a64` `alpha=0.8` | 有り（既定） | 9.27 | 14.45 |

⇒ **語彙検索の追加コストは p50 で約 +7.0ms、p95 で約 +11.6ms**（259チャンク・全探索）。
系統2 が **約4〜5倍**になっている。

🔑 **この差は「その日のマシンの機嫌」では説明できない。** 統制測定は同一セッション内で、
`with_embedding`（Ollama 往復＝マシン共有の影響を最も受ける系統）が 49.9 / 60.9ms と、
本測定の 60.1 / 72.7ms に対して**同じ桁で近い**まま、系統2 だけが 2.2 → 9.3ms へ動いている。
マシン全体が遅かったのなら両系統が一緒に動くはずである。

⚠️ **ただしこれは A/B ではなく前後比較である。** `742119a` と `b3f1a64` の間には語彙検索以外の
変更も入っている（CLI・SQLite ストア・ADR 0015 の合成方式）。系統2 の SQL を変えた変更は
語彙列の追加だけなので原因はほぼ特定できるが、**「+11.6ms のすべてが `ts_rank` である」とは
本測定は言っていない。** 内訳が要るなら `EXPLAIN ANALYZE` の仕事である。

### なぜ全行に `ts_rank` が掛かるのか（意図された状態）

`lexemes` 列に **GIN / GiST 索引を作っていない**。`0002_add_lexemes.sql` が理由を書いている——
ベクトル索引を最初から作らないのと同じ理由（ADR 0007）であり、
加えて現在の検索は `@@` で絞り込まず**全行に `ts_rank` を計算する**ので、そもそも転置索引が
使われる形になっていない。

⇒ **本書の系統2 の数字は、語彙側についても「索引を入れる前」の before である。**
ADR 0007 が「測ってから索引を入れた経路」を成果物と呼ぶのと同じ位置づけで、
Phase 1 項目7 で索引を検討するときの比較対象になる。

## 品質指標は rounds=1 と一致した

`rounds` は同じクエリを何周するかであって、順位付けは決定的である。したがって品質指標は
一致するはずであり、**一致した**。

| 構成 | | rounds=1（既存） | **rounds=5（本測定）** | |
| --- | --- | ---: | ---: | --- |
| ハイブリッド `alpha=0.8` | `recall@10` | 0.724 | **0.7241** | ✅ |
| ハイブリッド `alpha=0.8` | `MRR` | 0.807 | **0.8072** | ✅ |
| `alpha=1.0` | `recall@10` | 0.596 | **0.5960** | ✅ |
| `alpha=1.0` | `MRR` | 0.705 | **0.7055** | ✅ |

`alpha=1.0` の側は、基準線文書
（[`2026-09-02-eval-vector-only-baseline.md`](2026-09-02-eval-vector-only-baseline.md)）の
`recall@10` 0.596 / `MRR` 0.705 とも一致する。統制測定 `prelex-control` も同じ値を返した。

🔑 **リビジョンを跨いでも `alpha=1.0` は純ベクトルと同じ順位を返している。**
語彙検索を足したことで純ベクトルの挙動が壊れていないことの、副産物としての確認になっている。

`recall@1` / `recall@5` も含めた完全な内訳は JSON にある（本書では latency が主題なので省く。
品質の読み解きは [`2026-09-02-eval-lexical-hybrid.md`](2026-09-02-eval-lexical-hybrid.md) が正本）。

## 要件定義 §8 の予算に対する位置

要件定義 §8 の性能要件は **「1万チャンクに対し検索 p95 < 200ms（埋め込み往復を除く）」**。

| | 値 |
| --- | ---: |
| 既定構成の p95（系統2・**259チャンク**） | **14.4ms** |
| 予算 | 200ms |
| 予算に占める割合 | **約 7%** |

🔴 **これは §8 を満たしたという意味ではない。** §8 が言っているのは **1万チャンク**での話で、
本測定は **259チャンク**である。要件の 2.6% の規模でしか測っていない。

⚠️ **この 14.4ms から 1万件の数字を外挿しないこと。** 現在の検索はベクトルも語彙も
**索引なしの全探索**なので、走査コストは件数に比例する成分を持つ。単純に 38.6倍すれば
予算を超える計算になるが、固定費と可変費の比を本測定は分離していないので、
**その掛け算には根拠が無い。** 規模での実測は Phase 1 項目7 の仕事である。

🔴 **この節の「1万」と、項目7 の「10万」は別の数字である。混ぜないこと。**
**1万チャンク**は要件定義 §8 の**性能要件が課された規模**（p95 < 200ms）。
**10万件**は ADR 0007 / CLAUDE.md 項目7 が**実測せよと定めた規模**であり、
要件定義 §8 の「規模」行が Phase 1 の想定上限としている値でもある。
⇒ 項目7 の測定は §8 の予算より**1桁大きい規模**で行われる。片方に揃えて書き換えないこと。

🔑 むしろ本書が項目7 に渡す情報は絶対値ではなく**構成比**である——
系統2 の p50 のうち **76% が語彙検索側**（2.217ms → 9.268ms）で、これは索引の無い `ts_rank` の全行計算である。
⇒ **規模を上げたとき最初に効くのは、ベクトル索引（HNSW）だけとは限らない。**
ADR 0007 の手順は HNSW を想定して書かれているが、**測るべき索引は2つある。**

## 利用者から見た応答時間（系統1）

既定構成の p95 は **74.6ms**、p50 は 60.2ms。**その大半が Ollama への埋め込み往復**である
（系統2 が 14.4ms なので、残りが往復ぶん）。

🔴 **ただしここでも引き算をしていない。** 「往復は 60.2ms」とは書かない——
2つの分布のパーセンタイルの差は「差の p95」ではないからである（地雷10）。
言えるのは「系統1 の p95 が 74.6ms、系統2 の p95 が 14.4ms」という2つの実測値だけである。

max が 109.3ms まで伸びているのは GPU を他アプリと共有しているためで、
`min` 44.4ms との開きがそのまま共有環境のばらつきである。**占有環境ならこの幅は縮む。**

## この数字の限界

- **規模**: 259チャンク・索引なしの全探索。**10万件では別の数字になる**（項目7・ADR 0007）
- **前後比較であって A/B ではない**: 統制測定はリビジョンを跨いでおり、語彙検索以外の
  変更も含む。追加コストの内訳は本測定では分離していない
- **占有ベンチではない**: GPU は他アプリと共有。系統1 のばらつき（44〜109ms）はその反映
- **`alpha` は latency に効かない**（上記のとおり）。`alpha` を変えて速くする余地は
  現在の実装には無い。効かせたいなら「語彙を計算しない」という別の判断が要る
- **コーパスの偏り**: ADR・規約文書で `pgvector`・`org_id` のような識別子が濃い。
  `to_tsquery` が生成する bigram の数はクエリの文字数に依存するので、
  **一般の日本語文書での `ts_rank` のコストはここでの値と違いうる**

## 再現手順

```bash
docker compose up -d
set -a; . ./.env; set +a          # RECALL_DATABASE_URL と RECALL_OLLAMA_URL が要る
make eval EVAL_LABEL=hybrid-alpha-08-r5 EVAL_ALPHA=0.8 EVAL_ROUNDS=5 GPU_NOTE="占有状況を書く"
make eval EVAL_LABEL=vector-only-r5     EVAL_ALPHA=1.0 EVAL_ROUNDS=5 GPU_NOTE="占有状況を書く"
```

統制測定は `git worktree add --detach <path> 742119a` で語彙実装前のリビジョンを取り出し、
同じ `make eval` を走らせた（そのリビジョンの Makefile は `EVAL_ALPHA` を持たないが、
語彙検索が無いので `alpha` は順位の単調変換にしか効かず、latency にも影響しない）。

⚠️ `make eval` は `make check` に含まれない（CI に Ollama が無く、評価は検査ではなく計測だから。ADR 0013）。

🔑 **`git_modified: false` で測ること。** 3本とも作業木が clean な状態でビルドしている。
`make eval` の出力先が `docs/benchmarks/data/` なので、**前の測定の JSON が未追跡のまま残っていると
次のビルドが `git_modified: true` で刻まれる。** 連続して測るときは、前の成果物を一旦外へ退避する。
`data/README.md` が「`git_modified: true` は比較の基準線にしない」と書いているとおり、
正本にするレポートでここが `true` になっていてはならない。
