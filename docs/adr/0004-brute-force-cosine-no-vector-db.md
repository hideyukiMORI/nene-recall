# ADR 0004: ベクトル DB を使わず、総当たりのコサイン類似度で始める

## Status

**superseded by [ADR 0007](0007-pgvector-over-brute-force.md)** (2026-09-01)

> ⚠️ **性能分析は今も有効。** 10万件規模では総当たりで足りるという本 ADR の結論は覆っていない。
> 判断が変わったのは市場価値という別の軸が追加されたためで、性能上の必要からではない。
> 経緯は ADR 0007 を読むこと。

## Context

ベクトル検索の実装には概ね三つの道がある。

| 方式 | 依存 | 規模上限の目安 | 備考 |
| --- | --- | --- | --- |
| 専用ベクトル DB（Qdrant / Weaviate 等） | 別プロセス・別コンテナ | 数千万 | 自己ホストの配布が重くなる |
| SQLite 拡張（sqlite-vec 等） | **cgo** | 数百万 | cgo でクロスコンパイルの容易さを失う |
| Go 側で総当たり内積 | なし | 実測次第 | 単一バイナリを保てる |

Phase 1 の想定規模は個人の文書と SMB のコーパスで、**10万チャンク未満**。
1024次元 float32 の 10万件は約 400MB で、メモリに載る。
現代のCPUで10万件の内積は数十ミリ秒の水準に収まる。

加えて Voyage の埋め込みは**長さ1に正規化済み**であり、公式ドキュメントが
「コサイン類似度は内積と等価で、内積のほうが速く計算できる」と明記している。
正規化の処理すら要らない。

`voyage-4-nano` が Apache 2.0 で公開されている以上、将来ローカル埋め込みに寄せる道もあり、
その時に cgo 依存を抱えていると配布がさらに苦しくなる。

## Decision

**Phase 1 はベクトル DB も cgo も使わない。**

- 永続化は SQLite（純 Go ドライバ `modernc.org/sqlite`）。埋め込みは BLOB として保存
- 検索時は対象 org のベクトルをメモリに読み、**総当たりで内積**を取る
- 起動時にベクトルをメモリへロードし、投入・削除で差分更新する

**再評価のトリガーを先に決めておく:**

- チャンク数が **10万**を超えたとき
- または検索 p95 が **200ms** を超えたとき

どちらかに触れたら、この ADR を supersede して近似最近傍（HNSW 等）を検討する。

## Consequences

**得るもの**

- 単一バイナリ＋SQLite ファイルで配布できる。cgo 無しでクロスコンパイルが通る
- インフラ依存がゼロなので、個人利用の起動コストが実質ない
- 正規化済みベクトル前提で実装が単純になる（内積1本）

**払うもの**

- 規模が伸びると線形に遅くなる。10万件を超えたら作り直しが要る
- 全ベクトルをメモリに持つのでメモリ使用量がチャンク数に比例する

**リスクの明示**

- **この判断は「規模が小さいうちは正しい」だけで、正しさに期限がある。**
  上のトリガーを監視していなければ、遅くなってから気づくことになる。
  Phase 1 で検索レイテンシとチャンク数をログに出す（非機能要件に含める）
