# ADR 0013: 評価ハーネスは安定キーで正解を持ち、`make check` には含めない

## Status

accepted (2026-09-01)

## Context

[ADR 0009](0009-retrieval-evaluation-is-in-scope.md) は検索品質の評価を Phase 1 の必須要件と定め、
`recall@k`・`MRR`・`p95`（**埋め込み往復を含む／除く の両方**）を `make eval` で繰り返し測れる形にすると決めた。
本 ADR は、それを実装するときに避けて通れない設計判断を記録する。

判断が要る理由は、評価が「動くかどうか」ではなく**数字が後から検証できるかどうか**を成果物にするからである。
`docs/benchmarks/2026-09-01-baseline.md` の追記が示したとおり、モデルもランタイムも一致しているのに
§5 の絶対値が再現しなかった。**後から検証できない数字は正本になれない。**
評価ハーネスは同じ失敗を構造的に起こさない形で作る必要がある。

さらに、評価が動くより先に語彙検索（要件定義 Q-2: bigram か形態素か）とハイブリッド合成
（Q-3: `alpha` の最適値）を実装すると、どちらも当て推量で決めることになる。
`alpha = 0.7` に根拠が無いという現状は、まさにその過ちの結果である。
**測る仕組みを先に作る**というのが本 ADR の前提にある順序である。

なお本 ADR が扱うのはハーネス（測る仕組み）であって、評価セットの中身ではない。
`testdata/eval/` の本文とクエリ注釈は施主の判断を待つ。

## Decision

### 1. 正解セットは DB の `chunks.id` を持たない。安定キー `eval_key` で参照する

`chunks.id` は `GENERATED BY DEFAULT AS IDENTITY` の採番であり、取り込みのたびに変わる。
Phase 1 は insert-only で upsert を持たず、再取り込みは `DeleteBySource` → `Put` の2手順である
（`migrations/0001_create_chunks.sql`）から、**同じ文書を入れ直せば必ず別の id になる**。
正解セットに id を書くと、その正解セットは1回しか再現しない。

したがって正解は評価セット側の安定キーで持つ。

```
corpus.jsonl  : {"eval_key": "adr-0007#003", "content": "...", "tags": [...], ...}
queries.jsonl : {"query_id": "q-012", "text": "...", "relevant": ["adr-0007#003"], ...}
```

**採番 id への写像は実行時にメモリ上で作る。** `index.Writer.Put` は
「採番された id を入力と同じ順で返す」ことを契約としている（`internal/index/index.go`）ので、
評価ランナーが自分でコーパスを投入すれば、投入順 → 採番 id の対応が
**SQL を1本も足さずに**手に入る。

🔴 **この写像を永続化しない。** ファイルに落とすと「古い写像」という新しい不安定性が生まれ、
id を書いたのと同じ問題が一段遅れて再発する。写像は評価プロセスの寿命と同じにする。

**却下した案**: `chunks` に `eval_key` 列を足す。
評価のためだけの列を本番スキーマへ入れることになり、Corpus 統合（Phase 2）に持ち越される負債になる。
実行時の写像で足りるものにスキーマを払わない。

### 2. コーパスは JSONL で凍結する。実行時に `docs/` を分割しない

「評価コーパスは `docs/` の中身をその場で分割して作る」ほうが管理点は減るが、採らない。

文書を1文字直しても、あるいは分割器のパラメータを1つ変えても、**チャンクの境界が動く**。
境界が動くと `eval_key` の指す先が変わり、**人手で付けた正解注釈が静かに別のチャンクを指す**。
評価セットの中で最も高価な資産は人手の注釈であり、その参照先が勝手に動く設計は取れない。

JSONL に凍結すれば、コーパスは git の履歴を持つ不変の入力になる。
文書を更新したくなったら、コーパスを作り直して注釈も見直す——**それが明示的な作業になる**ことが要点である。

### 3. `postgres.Store.SearchVector` を公開する。ただし `index.Searcher` の契約には足さない

ADR 0009 は p95 を「埋め込み往復を**含む／除く** の両方」で測れと要求している。
現状の `Store.Search` は埋め込みの生成と SQL を続けて実行するので、DB 部分だけを分離して測れない。

そこで、埋め込み済みのベクトルを受け取る計測用の口を公開メソッドとして足す。

```go
func (s *Store) SearchVector(ctx context.Context, q index.Query, vector []float32) ([]index.Result, error)
```

🔴 **`index.Searcher` には足さない。** これは計測のための口であって「検索する」という契約の一部ではない。
契約に入れると、すべてのストア実装（Phase 1 項目8 の SQLite を含む）が計測の都合に付き合わされる。
`Ping` を `embed.Embedder` の契約に入れなかったのと同じ判断軸である（ADR 0012 の周辺）。

🔴 **SQL は既存の `searchSQL` を共有する。** 実体は `validateQuery` + `validateVector` +
`encodeVector` + 既存の `searchRows` であり、`Search` 自身もこれを通る形に組み替える。
計測対象と本番経路が別の SQL を持つと、測った数字が本番の数字でなくなる。

**却下した案**: 評価ランナー側が SQL を書いて直接 DB を叩く。
`internal/eval` から `database/sql` と pgvector の演算子を知ることになり、
ARC-001 の依存方向を壊すうえ、**計測している SQL が本番の SQL と乖離しても誰も気づかない**。
これは QLT-008（性能の主張は実測を伴う）が守ろうとしているものを、形だけ満たして中身で裏切る形になる。

**却下した案**: `Search` に「ベクトルを渡す」オプション引数を足す。
GO-011 の引数上限に触れるうえ、本番経路に計測専用の分岐が入る。分岐は必ずいつか間違った側に倒れる。

### 4. p95 は2系統を**それぞれ実測**する。引き算で出さない

- 系統1（埋め込みを含む）= `Search`
- 系統2（埋め込みを除く）= `SearchVector`（クエリベクトルは事前に1回だけ生成する）

🔴 **系統2を「系統1の p95 から埋め込みの p95 を引く」形で求めない。**
異なる分布のパーセンタイル同士の引き算に統計的な意味は無い（p95 同士の差は差の p95 ではない）。
両方を実測する。

計測手順は固定する。

1. 全クエリを1周ウォームアップする（**計測に含めない**）。
   モデルのコールドスタートは実測 18.4 秒（`docs/benchmarks/2026-09-01-baseline.md`）で、
   これが1サンプル混ざるだけで p95 が壊れる
2. 各クエリを既定5回ずつ実行し、全サンプルから p50 / p95 を出す
3. 品質指標（`recall@k`・`MRR`）は1周目の結果から算出する。
   検索は決定的なので、繰り返しても順位は変わらない

### 5. `make eval` を `make check` に含めない。ただし決定的な部分は含める

QLT-003 は「`make check` が唯一の入口」と定めており、これはその緊張関係に対する明示的な線引きである。

**含めない理由は2つある。**

1. **CI に Ollama も GPU も無い。** 偽の Embedder で `recall@10` を測っても、それは
   偽の Embedder の性質を測っているだけで、検索品質の評価にならない
2. **評価は「検査」ではなく「計測」である。** `recall@10 = 0.83` は真でも偽でもない。
   ADR 0009 自身が「数十クエリで測った recall を過信するな。方向性を見るための道具である」と
   明記しており、その粒度の指標に自動 fail の閾値を切ると、**1クエリ分のゆらぎで CI が赤くなる**。
   赤が意味を持たなくなれば、ゲート全体の信頼が落ちる（QLT-002 が baseline を拒否したのと同じ理由）

**含めるもの**（QLT-003 の精神への配慮）:

- `internal/eval` の指標計算とローダのユニットテスト。純粋関数であり、依存も非決定性も無い
- **評価セットの整合性テスト**——`queries.jsonl` の全 `relevant` キーが `corpus.jsonl` に実在すること・
  `eval_key` に重複が無いこと・タグが既知集合に属すること・`note` が空でないこと。
  これらは**真偽が決まる検査**であり、計測ではない。
  ⇒ **評価セットを壊すコミットは CI で落ちる。**

整合性テストは `testdata/` の読み取りに `os` を要するので `cmd/eval` のテストとして置く
（`internal/eval` は ARC-005 により `os` を import できず、`cmd` はその除外対象である）。

### 6. 評価に LLM を使わない（ADR 0009 の再確認）

`recall@k` と `MRR` は正解セットとの突き合わせであり、純粋な集合演算で計算できる。
ハーネスは LLM を1回も呼ばない。`ragas` の faithfulness のような LLM 審査員は**生成の評価**であって、
生成は Recall のスコープ外である（要件定義 §3.3）。

**結果として、最も価値の高い検証が最も費用のかからない方法で行える。**
将来この性質を壊す変更（「LLM に関連度を判定させる」等）は、本 ADR と ADR 0009 を
supersede する形でしか入れられない。

### 7. レポートは JSON。集計値を生データから再計算できること

`-out` に書く JSON には次を必ず入れる。

| 区分 | 内容 |
| --- | --- |
| 環境 | git commit（`runtime/debug.ReadBuildInfo` の `vcs.revision`）・`Embedder.ID()`・**Ollama の版とモデル digest**・PostgreSQL と pgvector の版・GPU 占有状況の自己申告 |
| 入力の同一性 | `corpus.jsonl` と `queries.jsonl` の **sha256**・チャンク数・クエリ数 |
| 条件 | `alpha`・`limit`・ラウンド数・計測日時 |
| **per-query の生データ** | クエリごとの上位 `eval_key` 列・各正解の順位（圏外は `null`）・各ラウンドの latency 2系統 |
| 集計値 | `recall@1/5/10`・`MRR`・p50/p95（2系統）・**タグ別 `recall@10`** |

🔴 **per-query の生データを必ず残す。** これがベンチ追記の教訓
「後から検証できない数字は正本になれない」への直接の回答である。
集計値だけのレポートは、それが正しいことを第三者が確かめられない。
生データがあれば、集計の実装が間違っていても後から気づける。

**タグ別 `recall@10` を併記する。** 数十クエリの総合値は動きにくく、
「どのカテゴリが壊れたか」のほうが診断情報として濃い。

**モデル digest は自動取得する。** ベンチ追記が残リスクとして
「`Embedder.ID()` は `bge-m3:1024` であり digest もランタイム版も含まない。
同じタグで別の重みが引かれても ADR 0005 の不一致検知は発火しない」と記録している。
`embedder_id` の書式を変えるのは再取り込みを伴う別判断なので、
**レポート側で穴を塞ぐ**（記録に残せば、後から digest 違いを突き合わせられる）。

実測で確かめた取得経路（2026-09-01・Ollama 0.33.2）:

| エンドポイント | digest |
| --- | --- |
| `POST /api/show` | **含まれない**（`details`・`model_info`・`tensors` はあるが digest フィールドが無い） |
| `GET /api/tags` | **含まれる**（`models[].digest` = 64桁の16進） |
| `GET /api/version` | ランタイム版（`{"version":"0.33.2"}`） |

⇒ digest は `/api/tags` から取る。`Ping` が使う `/api/show` では取れない。

⚠️ `/api/tags` の `name` は `bge-m3:latest` で、設定値 `RECALL_EMBED_MODEL=bge-m3` とは一致しない。
タグを省略した指定は `:latest` を意味するので、照合はそれを解いてから行う。
**一致しなかったときは digest を空にして続行する**——digest はレポートの付帯情報であって、
評価そのものを止める理由にならない。

取得は `internal/embed/ollama` にメソッドを足す形にし、**`embed.Embedder` の契約には足さない**。
これは `Ping` と同じ扱いである（ランタイムの素性は「テキストをベクトルに変換する」契約の一部ではない）。

### 8. 評価専用の DB `recall_eval` を毎回作り直す

開発用の `recall` にもテスト用の `recall_test` にも相乗りしない。
無関係な行が1件でも混ざれば、それは順位に入り込んで `recall@k` を汚染する。
評価は「このコーパスに対する順位」を測るものなので、コーパス以外が入っていてはならない。

毎回 DROP → CREATE → `Migrate` → 投入する。既存の `main_test.go` の
`recreateTestDatabase` と同じ流儀である（前回の残骸に依存して「たまたま通る」状態を作らない）。

🔴 **ポート 5433 の同期箇所が 4 から 5 に増える**（`compose.yaml`・`.github/workflows/ci.yml`・
`.env.example`・`main_test.go` に `cmd/eval` の既定 DSN が加わる）。
5433 なのは 5432 をネイティブ PostgreSQL が占有しているためで、
標準ポートに戻すと「コンテナは healthy なのに SASL 認証失敗」という辿りにくい壊れ方をする。

### 9. `k ∈ {1, 5, 10}`・`limit = 10`

`recall@10` が主指標で、`recall@1` は「一発で当たるか」、`recall@5` はその中間を見る。
`limit` を 10 に固定するのは `recall@10` の計算に必要な最小限だからである。

⚠️ 正解が 10 件を超えるクエリの注釈が生まれたら、この選択は再判断が要る
（`recall@10` の上限が 1.0 に届かなくなる）。

### 10. `Makefile` の `build` は `./cmd/recall` のまま広げない

`cmd/eval` を `build` の対象に足さない。`build` は「配布する成果物を作る」ターゲットであり、
評価ランナーは開発者の道具であって成果物ではない。意味を変えない。

コンパイルの破壊は既に検知される——`make check` は `go vet ./...` と `go test ./...` を通すので、
`cmd/eval` が壊れればそこで落ちる。**検知されない穴を埋めるための変更ではない**ので、足す理由が無い。

## Consequences

**得るもの**

- 要件定義 Q-2（bigram か形態素か）と Q-3（`alpha` の最適値）を、議論ではなく実測で決着させる土台ができる。
  どちらも ADR 0009 が「評価で決める」と定義した未決事項である
- ADR 0007 の「測ってから HNSW を入れる」が実行可能になる。索引の before/after を同じハーネスで測れる
- レポートが per-query の生データを持つので、**集計値を第三者が再計算できる**。
  ベンチ §5 で起きた「再現できない数字」が構造的に起きにくくなる
- 評価セットを壊すコミットは CI で落ちる。人手の注釈という最も高価な資産が守られる

**払うもの**

- 評価コーパスの JSONL を作り直す手間が、文書を更新するたびに発生する。
  これは自動化の放棄ではなく、**注釈の参照先が黙って動かないことへの対価**である
- `SearchVector` という公開メソッドが1つ増える。契約ではないので実装ごとに有無が違ってよいが、
  「なぜ `Searcher` に無いのか」は本 ADR を読まないと分からない
- 評価の実行には Ollama と GPU が要る。CI では走らないので、**回帰の検出は人が `make eval` を
  実行したときにしか起きない**。ADR 0009 の「数値が下がったら気づける状態」は、
  実行を人の規律に依存している

**やらないこと**

- 評価セットの中身（`testdata/eval/` の本文とクエリ注釈）。施主の判断待ちであり、本 ADR の射程外
- 閾値による自動 fail。理由は Decision 5
- 評価結果の時系列比較の自動化。まず1点を正しく測ることを先にする
