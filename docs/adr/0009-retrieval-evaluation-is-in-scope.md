# ADR 0009: 検索品質の評価を Phase 1 のスコープに含める

## Status

accepted (2026-09-01)

## Context

当初の要件定義では、Phase 1 のスコープは「検索が動くこと」までで、
**検索が良いかどうかを測る仕組みは含まれていなかった**。

しかし裏取りの結果、これが最大の抜けだと判明した。2026年時点の一般的な知見:

> コサイン類似度とメタデータフィルタは全製品が対応済みであり、
> 差がつくのは運用コスト・既存基盤との統合性・チームのスキルセット

つまり**ベクトル DB の選定も、コサイン類似度の実装も、もう差別化にならない**。
誰でも数行で書ける領域である。

一方で、次の問いに数字で答えられる実装は少ない:

- ハイブリッド検索の重み `alpha` を 0.7 にした根拠は何か
- 日本語の分割を bigram にした場合と形態素にした場合で、検索品質はどれだけ違うか
- HNSW 索引を入れると recall はどれだけ落ちるか。その劣化は許容範囲か

**これらはすべて「測っていなければ答えられない」問いである。**
そして ADR 0007 が「測ってから索引を入れる」を成果物と定義した以上、
測る仕組みが無ければその ADR は実行できない。

## Decision

**検索品質の評価を Phase 1 の必須要件とする。** 実装が動くだけでは Phase 1 完了と見なさない。

### 測るもの

| 指標 | 内容 |
| --- | --- |
| `recall@k` | 正解チャンクが上位 k 件に含まれる割合 |
| `MRR` | 最初の正解が現れた順位の逆数の平均 |
| `p95 latency` | 検索の応答時間（埋め込み往復を含む／除く の両方） |

### 評価セット

- `testdata/eval/` に「クエリ ↔ 正解チャンク ID」の対応を JSON で持つ
- **日本語を主対象とする。** 想定用途が日本語文書なので、英語ベンチマークでは意味がない
- 手で作る。規模は小さくてよい（数十クエリ）——無いより桁違いにましである

### 🔑 評価に LLM を使わない

**検索の評価に LLM は要らない。** `recall@k` と `MRR` は正解セットとの突き合わせであり、
純粋な集合演算で計算できる。LLM を1回も呼ばない。

`ragas` の faithfulness のような LLM 審査員を使う指標は、**生成の評価**であって
検索の評価ではない。Recall のスコープは取得までなので（要件定義 §3.3）、そもそも対象外である。

この帰結として、**最も価値の高い部分の検証が、最も費用のかからない方法で行える**。

### 回帰として固定する

評価は一度きりの計測ではなく、`make eval` で繰り返し実行できる形にする。
`alpha` の変更・分割方式の変更・索引の追加のたびに走らせ、
**数値が下がったら気づける状態**を保つ。

## Consequences

**得るもの**

- ADR 0007 の「測ってから索引を入れる」が実行可能になる
- `alpha` の既定値 0.7 に根拠が付く。現状これは**根拠のない当て推量**である
- 要件定義 Q-2（bigram か形態素か）を、議論ではなく実測で決着できる
- 実戦価値の観点で最も説明力の高い成果物になる。
  「Qdrant を使った」より「recall と p95 のトレードオフから索引を入れる閾値を決めた」のほうが強い

**払うもの**

- Phase 1 の完了が遅れる。評価セットを手で作る手間がかかる
- 評価セットは小規模なので、**統計的な厳密さは無い**。
  数十クエリで測った recall を過信しないこと。方向性を見るための道具である

**やらないこと**

- 生成品質の評価（faithfulness・answer relevancy 等）。Recall のスコープ外
- 公開ベンチマーク（MTEB 等）への追従。用途が日本語の自前文書なので、
  汎用ベンチマークのスコアは判断材料にならない
