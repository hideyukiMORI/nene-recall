# ADR 0019: 10万件規模の実測は日本語 Wikipedia を「無関係文書」として足して行い、埋め込みはディスクに再利用する

## Status

accepted (2026-09-02) — データ源は施主判断（2026-09-02「Wikipedia」）

## Context

[ADR 0007](0007-pgvector-over-brute-force.md) は「10万件規模で p95 と recall を測ってから索引（HNSW）を入れる」経路を
価値の中心に置いた。[latency 正本](../benchmarks/2026-09-02-eval-hybrid-latency.md) は、測るべき索引が HNSW だけでなく
`GIN (lexemes)` もあることを示した。評価セットは 259 チャンクしかなく、10万件の日本語文書が要る。

規模の実測で見たいものは2つ:
1. **latency**: 全探索の p95 が 10万件でどこまで伸びるか（要件 §8 は 1万件で 200ms）
2. **recall の希釈**: 正解 236 件の周りに無関係な文書が 10万件あるとき、上位 10 件に正解が残るか。
   索引（HNSW）は近似なので、索引の前後で recall が落ちるかも同時に見る

### 制約

- 費用 0 円・ライセンス明記（Wikipedia は CC BY-SA 4.0。帰属を文書に残す）
- **評価セット（`testdata/eval/`）は 1 バイトも変えない**。正解注釈は 259 チャンクの上にある（ADR 0013）
- 10万件をリポジトリにコミットしない（数十 MB）。取得手順とチェックサムで再現性を担保する
- 10万件の埋め込みは約 18 分（Q-7 実測 88〜93 件/秒）。**評価のたびに埋め込み直すと 1 構成 20 分**になり、
  `alpha` 掃引や before/after が現実的でなくなる

## Decision

### 1. 無関係文書（distractor）として日本語 Wikipedia の本文を使う

取得元は Wikimedia の公式ダンプ。形式は実装レーンが確認して選ぶ（優先順: CirrusSearch の content dump の `text` /
`pages-articles` の第1パート）。段落単位に切り、**100〜500 字**の段落を 10万件、決定的に選ぶ（ページ ID 昇順・先頭から）。
`document_id` / `source_id` は評価セットと衝突しない範囲（例: 9,000,000 以降）。`eval_key` は持たない（正解にならない）。

### 2. 評価ハーネスに `-distractors <jsonl>` を足す。正解セットの意味は変えない

distractor は投入されるが、どのクエリの正解にもならない。`recall@k` / `MRR` の定義は変わらず、
「正解 236 件が distractor に押し出されたか」がそのまま数字に出る。レポートの `conditions` に distractor の件数と
sha256 を記録する（記録が無いと 259 件の数字と並べて読めない）。

### 3. 埋め込みをディスクに再利用する（`-embed-cache <dir>`）

キーは `sha256(embedder_id + "\x00" + kind + "\x00" + text)`、値は float32×次元の生バイト。**embedder_id をキーに含める**ので
モデルを替えれば自動的に別のキャッシュになる（ADR 0005 の罠を踏まない）。キャッシュは `bin/` 配下（gitignore 済み）。
🔴 **系統1（埋め込み往復を含む）の latency はクエリ側の埋め込みで測る**。クエリの埋め込みは**キャッシュしない**
（キャッシュすると系統1 が系統2 と同じになり、2系統の意味が消える）。

### 4. 索引は測ってから、**別 PR・別 ADR** で入れる

本 ADR はデータと計測の口だけ。`CREATE INDEX … USING hnsw` と `GIN (lexemes)` の導入判断は before の数字が出てから
ADR 0020 系で行う（ADR 0007 の手順 3）。

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| **評価セットを 10万件に増やす（正解注釈も）** | 注釈は人手で、第二注釈者との突き合わせが要る。規模の実測に必要なのは「正解の周りの無関係文書」であり、正解の数ではない |
| **合成文書（テンプレート・乱数）** | 語彙もベクトルも分布が現実と違い、`ts_rank` と HNSW の挙動が実データと乖離する。「10万件で測った」と言えなくなる |
| **施主の実文書** | 施主判断で Wikipedia。公開リポの再現性（第三者が同じデータを得られる）でも Wikipedia が勝る |
| **Wikipedia API でランダム取得** | 10万リクエスト。非決定的で再現できない |
| **クエリ埋め込みもキャッシュ** | 系統1 の意味が消える（Decision 3） |
| **キャッシュを SQLite / Postgres に置く** | 評価 DB は毎回作り直すので消える。ファイルが最も単純で、ストアを跨いで共有できる |

## Consequences

- 初回だけ約 20 分（ダウンロード＋埋め込み）。以後は数十秒で 10万件を投入できる（Postgres の COPY 相当のバッチ投入が要る）
- `docs/benchmarks/` に「10万件・索引なし」の正本を残し、それが HNSW／GIN 導入の before になる
- SQLite は本測定の対象外（259 件で既に予算を使い切っている。ADR 0017 追記）
