# ADR 0003: `org_id` を全 API で必須とし、欠落は 400 で落とす

## Status

accepted (2026-09-01)

## Context

Corpus はマルチテナントであり、テナント分離は**SQL の WHERE 句に埋め込まれている**
（`nene-corpus/src/Search/PdoChunkSearchRepository.php:73`）:

```sql
WHERE (...) AND c.organization_id = ?
```

`org_id` は `RequestScopedOrgIdHolder` からミドルウェア経由で注入され、
未解決なら `LogicException` を投げる（同 `:29-35`）。つまり Corpus 側では
**分離の失敗が例外として顕在化する**設計になっている。

検索を Recall に外出しすると、この分離責任が Go 側へ移る。
ここで `org_id` を任意パラメータにしたり、未指定時に既定 org へフォールバックしたりすると、
**あるテナントの検索が別テナントの文書を返す**——マルチテナントの情報漏洩になる。

しかもこの種の欠陥は、単一テナントで開発・テストしている限り一切症状を出さない。

## Decision

- `POST /v1/search`、`POST /v1/chunks`、および全ての削除系で **`org_id` を必須**とする
- 未指定・空・0・非数値はいずれも **400 を返す**。既定値へのフォールバックを実装しない
- ストア層のクエリは `org_id` を**引数として要求する**シグネチャにし、
  呼び出し側が渡し忘れたらコンパイルが通らないようにする
- 「全 org 横断検索」の機能を作らない。必要になったら別 ADR で改めて判断する

## Consequences

**得るもの**

- 分離漏れが実行時のデータ流出ではなく、開発時のコンパイルエラーか 400 として出る
- 個人利用（org が1つ）でも同じ経路を通るので、統合時に初めて経路が変わることがない

**払うもの**

- 個人利用では常に同じ `org_id` を渡す手間がある。CLI 側の既定値で吸収する
  （**サーバ側には既定値を置かない**——ここが要点）

**追随作業**

- `org_id` の異なる2件を投入し、一方の検索が他方を返さないことを確認するテストを、
  Phase 1 の最初のテストとして書く
