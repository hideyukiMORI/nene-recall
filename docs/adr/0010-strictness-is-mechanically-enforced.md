# ADR 0010: 厳格性は文章ではなく機械で強制する

## Status

accepted (2026-09-01)

## Context

施主から前提が示された（2026-09-01）:

> NENE2 レベルに厳格にしたい。というか NENE2 以上に厳格にしたい。
> 一つの事を実装しようとすると一つの方法を必ず取る必要がある状態が理想。

参照する先行事例が2つある。`NENE2`（PHP・PHPStan level 8 ＋ `composer check` に7つの検査を束ねる
＋ 自作の `tools/conformance.php`）と、`NENE-PIXEL`（Kotlin・`KOT-001`〜`KOT-022` / `ARC` / `QLT` の
規則 ID と「機械強制: active / planned」を並べた表、baseline 禁止、waiver 手続き）である。

**問題は、Kotlin で成立しているものが Go でそのまま成立しないことである。** 実測した:

```go
func Search(o OrgID)          // type OrgID int64

Search(raw)              // ❌ コンパイルエラー（int64 変数は渡せない）
Search(1)                // ✅ 通る    未型付き定数は暗黙変換される
var z OrgID; Search(z)   // ✅ 通る    ゼロ値がコンストラクタを迂回する
var c Cfg                // ✅ 通る    不変条件を持つ型がゼロ値で作れる
unused := 42             // ❌ コンパイルエラー（Go では未使用ローカル変数はエラー）
```

封印インタフェース（未公開メソッドで外部実装を封じた型）に対する**網羅漏れの type switch も
コンパイラは通した**。

つまり Go には以下が無い。

| NENE-PIXEL の規則 | Go の言語機能 |
| --- | --- |
| KOT-002 不正状態を表現不能にする・`else` なし exhaustive | **無い**（sum type が無く、網羅性を言語が見ない） |
| KOT-003 公開状態は不変（`val`） | **無い**（不変性の言語支援がゼロ） |
| KOT-004 `null` は一意の意味・`!!` 禁止 | **不十分**（nil に加えてゼロ値の穴がある） |
| KOT-007 private コンストラクタ＋唯一のファクトリ | **不十分**（可視性は exported / unexported の2段のみ） |

一方で Go が Kotlin・PHP より強い点もある。未使用変数と未使用 import が**コンパイルエラー**であること、
`internal/` が**コンパイラに強制される**層境界であること、既定引数とオーバーロードが**言語に無い**こと
（＝「一つの事に一つの方法」が仕様で担保される領域がある）、`-race` が一級のゲートであること。

**そして、いま Phase 1 の実装が空である。** 規則を後から被せると既存違反を凍結する baseline が
必要になり、それは NENE-PIXEL の `QLT-002` が名指しで禁じているものである。
違反ゼロから始められる時点は今しかない。

## Decision

**厳格性を「規約文書」ではなく「落ちる仕組み」として実装する。** 三層で強制する。

| 層 | 何を守るか | 実体 |
| --- | --- | --- |
| コンパイラ | 層境界・cgo 排除・未使用宣言 | `internal/`、`CGO_ENABLED=0`、Go 本体 |
| 汎用の静的解析 | Go として危ういこと | `.golangci.yml`（採用した linter は全て規則 ID を持つ） |
| **自作の規約検査** | **NeNe Recall として守るべきこと** | **`tools/conformance`（標準ライブラリのみ）** |

具体的な決定は次のとおり。

1. **規則の正本を `docs/coding-rules.md` に置く。** すべての規則に ID（`GO-` / `ARC-` / `QLT-` / `CNF-`）を与え、
   機械強制の状態を **active / planned / 不採用** で明示する。**planned を active と書かない。**
2. **`make check` を唯一の入口とする。** CI は `make check` を呼ぶだけにし、CI 側にしか無い検査を作らない。
   「手元で再現できない失敗」を構造的に消すため。
3. **baseline を持たない。** `new-from-rev` も既定の除外プリセットも使わない。違反ゼロから始める。
4. **抑制には理由を要求する。** `//nolint` は linter 名と理由の両方が無いと `nolintlint` が落とす。
5. **ゲートを弱める変更は ADR を要する。** 閾値・除外・linter の削除・規則の降格が対象。
   CI は該当ファイルの差分を PR に通知する。
6. **`org_id` の分離を型と検査器で守る。** `org.ID` 型を導入し、生成経路を `org.NewID` / `org.ParseID` に限る。
   Go には private constructor が無いため、`org.ID(1)` という直接変換の禁止は
   **型ではなく `tools/conformance` の CNF-001 が担う**。
7. **道具のバージョンを固定する。** `golangci-lint` は `Makefile` の `GOLANGCI_VERSION` で固定し、
   一致しない版が入っていれば入れ直す。再現しないゲートは判定に使えない。

### 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| golangci-lint の既定セット（5 linter）だけ使う | 規則と linter の対応が付かず、「なぜ有効か」を説明できない。厳格さが道具の既定値に委ねられる |
| `enable-all: true` | 相互に矛盾する linter が同時に入る。実際 `wsl`（空行）・`nlreturn`・`varnamelen` は Go の慣用と正面から衝突し、規則ではなく道具の機嫌に従うことになる |
| `golang.org/x/tools/go/analysis` で自作アナライザを書く | 型情報が使えて強力だが、**go.mod に依存が入る**。現在の依存はゼロで、`CNF-001`〜`CNF-004` は構文で判定できる。型情報が要る規則が出てきた時点で本 ADR を supersede して再検討する |
| 規約を `CLAUDE.md` にだけ書く | 人間と AI の遵守に依存する。実際 `org_id` の規約は既に CLAUDE.md にあったが、守っているのはテスト10ケースだけで、新しく書かれるコードには及んでいなかった |
| Phase 1 の実装後に導入する | 既存違反を凍結する baseline が必要になる（QLT-002 と矛盾）。今なら違反ゼロで始められる |
| `noinlineerr` を有効にして `if err := f(); err != nil` を禁止する | 一形式に統一する意図には合うが、**禁止する側が Go の標準的な書き方であり、かつ err のスコープを狭める安全な形式**である。安全性を下げる方向の統一なので採らない |

## Consequences

**得るもの**

- 規則が「読まれなければ効かないもの」から「書いた瞬間に落ちるもの」になる。
  次に書くのが人間でも AI でも、遵守が意思に依存しない
- `org_id` の分離（ADR 0003）が、テスト10ケースの守備範囲から**全ファイルの検査**に広がった
- ローカルと CI が同一。ゲートの再現性が道具のバージョン固定まで含めて担保される
- 違反ゼロから始まるので、「既存違反があるから」を理由に規則が緩む経路が無い

**払うもの**

- 書き味に制約が入る。`err113`（動的 error 禁止）・`wrapcheck`（境界での包み込み必須）・
  `sloglint` の属性スタイル強制は、いずれも「短く書く」ことを妨げる
- 道具の保守が要る。`golangci-lint` のバージョン更新、`tools/conformance` の規則追加
- `tools/conformance` は型情報を持たないので、判定は識別子の名前と構文に依存する。
  名前を変えられると検査をすり抜ける

**正直に記録しておくこと**

- 🔴 **Go は Kotlin と同水準にはならない。** ゼロ値・不変性・網羅性の3つは言語で強制できず、
  静的解析でも完全には塞げない。特に `var id org.ID` は**どうやっても書ける**。
  この ADR が達成するのは「不正な状態を表現不能にする」ではなく
  「**不正な状態を書いたら CI が落ちる**」であり、両者は同じではない
- **本 ADR の厳格さは、実装がまだ空である今だからこそ無傷で導入できた。**
  緑であることは、規則が良いことの証明ではない。検査対象がまだ小さいことの結果でもある。
  Phase 1 で規則が邪魔になったとき、緩めるのではなく **ADR で判断を残すこと**が本 ADR の眼目である
- `golangci-lint` 自体のライセンスは **GPL-3.0**（実測: モジュールキャッシュの LICENSE）。
  別プロセスで走る開発用の道具であり、本リポジトリの MIT ライセンスには影響しない。
  ただし配布物に同梱しないこと

**追随作業**

- `docs/coding-rules.md` で planned としている規則（GO-006 の `any` 禁止、GO-012 の1ファイル1主要宣言等）を
  順次 active にする。着手前に planned を active と書き換えないこと
- Phase 1 で Postgres ストアを足すとき、`unqueryvet`・`sqlclosecheck`・`rowserrcheck` が
  初めて実際に効く。有効化済みだが、まだ一度も対象コードを見ていない
