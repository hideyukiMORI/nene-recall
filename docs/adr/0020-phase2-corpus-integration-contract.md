# ADR 0020: Phase 2 — Corpus 統合の契約。外部 ID・文書単位の削除・共有トークン・同期書き込み

## Status

accepted (2026-09-02) — 施主判断（2026-09-02「可能ならすぐ」）で Phase 2 に着手

## Context

[ADR 0001](0001-standalone-first-corpus-swappable.md) は「単体で完結し、Corpus の検索バックエンドとして環境変数ひとつで
差し替えられる」形を求めた。Corpus 側の `ChunkSearchResult::$score` の float 化（ADR 0006・`nene-corpus#385`）は済み、
型の壁は無い。残っているのは**契約**である。Corpus 側を読み取り調査（2026-09-02）した結果、決めるべき点は4つに絞れた。

| 事実（Corpus 側） | 帰結 |
| --- | --- |
| 検索の消費者は Claude のツール `search_corpus` だけ（HTTP ルート無し・OpenAPI に出ない） | 差し替えの影響範囲は Corpus の外部契約に出ない |
| `ChunkSearchRepositoryInterface::search(string $query, int $limit): list<ChunkSearchResult>`。org は `RequestScopedOrgIdHolder` から実装が引く | Recall 実装も同じ規約。`org_id`（int）をそのまま渡す |
| `CorpusSearchTool` は `Chunk::$id`（Corpus の chunks.id）が null だと例外 | **Recall は Corpus 側の id を返せなければならない** |
| chunks の INSERT / DELETE は `PdoChunkRepository` の `save` / `deleteByDocumentId` / `deleteBySourceId` の3点だけ | 同期の縫い目は3点。**文書単位の削除**が Recall に無い |
| sources / documents は soft delete、chunks は hard delete。検索 SQL は `is_deleted = 0` の join で保険を掛けている | Recall に削除を伝え損ねると消した内容が返る。Corpus 側に二段の保険が要る |
| 外部呼び出しの先例は `HttpNeneRecordsClient`（fail-soft・timeout 5s・Bearer 任意） | クライアントの形はこれに倣う。失敗時の挙動だけは検索の性質に合わせて別に決める |
| 依存方向は「Corpus → 上流 API」で逆流禁止（Corpus ADR 0002） | **Recall は Corpus を呼ばない。** Webhook で Corpus に通知する形は取れない |
| 認証は JWT fail-close（Admin 用） | サービス間は別。共有トークンで足りる |

現行 OpenAPI は `ChunkInput.chunk_id` を「Phase 1 では 400。受け入れ方式は Phase 2 の ADR で決める」と留保していた。本 ADR がそれである。

## Decision

### 1. Corpus 側の id は **`external_id`** として受け、Recall の `chunk_id` とは別に持つ

- `ChunkInput` に `external_id`（int64・任意）を足す。`UNIQUE (org_id, external_id)`（NULL は制約対象外）。
- `SearchResult` と `putChunks` の応答に `external_id`（nullable）を足す。`chunk_id` は従来どおり Recall の採番。
- **`chunk_id` を要求に書くのは引き続き 400**（エラーメッセージで `external_id` を案内する）。
  理由: `GENERATED BY DEFAULT AS IDENTITY` に明示 id を書くとシーケンスが進まず、後続の採番が衝突する。
  「外部の識別子」と「自分の採番」を1つの列に混ぜない。
- 同じ `(org_id, external_id)` を再投入したら **置き換え**（`ON CONFLICT DO UPDATE` で content・埋め込み・lexeme を更新）。
  Corpus の `DocumentChunkReplacer` は delete → save なので通常は当たらないが、リトライで二重投入されても壊れない。

### 2. `DELETE /v1/documents/{document_id}/chunks` を足す

Corpus の削除経路が document 単位と source 単位の2つだからである。`deleted` 件数を返す形は source 版と同じ。

### 3. 認証は**共有 Bearer トークン**（`RECALL_API_TOKEN`）。設定時は `/v1/*` 全部に必須、`/healthz` `/readyz` は不要

- 未設定なら認証なし（個人のローカル利用が既定）。設定されていれば `Authorization: Bearer <token>` が一致しない要求は 401。
- 比較は定数時間（`crypto/subtle`）。トークンはログに出さない（`config.Config` に `String()` を実装していない理由と同じ）。
- JWT は採らない（却下表）。Q-6 はこれで決着。

### 4. 同期は **Corpus からの同期書き込み**（write-through）＋**再索引コマンド**（Q-5）

- Corpus の `ChunkRepositoryInterface` にデコレータを重ね、`save` → Recall へ `POST /v1/chunks`（`external_id` 付き）、
  `deleteByDocumentId` / `deleteBySourceId` → Recall の対応する DELETE。**取り込み時の Recall 失敗は fail-loud**
  （取り込みは管理操作であり、静かに索引が欠けるより止まる方がよい）。
- 取り消し（DB ロールバック後に Recall だけ残る）と失敗の取りこぼしは、Corpus 側の**再索引コマンド**（全 chunks を
  Recall へ流し直し、Corpus に無い `external_id` を Recall から消す）で回収する。
- Webhook・ポーリングは採らない（却下表）。

### 5. 検索の失敗時、Corpus は **LIKE 検索へフォールバックし、警告ログを出す**

Recall に届かない・5xx のときに空を返すと、Claude が「根拠なし」で答える。従来の `PdoChunkSearchRepository` は
そのまま残るので、それに倒す。**フォールバックしたことは必ずログに残し**、`/health` 相当で Recall の状態を見せる。
厳格運用のためにフォールバックを切る設定（`NENE_RECALL_STRICT=1` → 例外）を持つ。

### 6. Corpus 側は Recall の結果を **soft delete で二段フィルタ**する

Recall の結果の `external_id` 群を1本の SQL で `chunks JOIN sources JOIN documents WHERE is_deleted = 0 AND organization_id = ?` に
通し、生きているものだけを返す。Recall への削除伝達が遅れても、消した内容が回答に混ざらない。
この SQL は `Pdo*Repository` の中に置く（Corpus の層規約）。

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| **`chunk_id` に Corpus の id を書かせる（identity 列へ明示 id）** | シーケンスが進まず採番が衝突する（OpenAPI の留保どおり）。外部識別子と自分の採番を混ぜない |
| **Recall の `id` を Corpus の id と一致させる（採番を Corpus に委ねる）** | Recall 単体利用（`recallctl`）で id が無い。Phase 1 の契約を壊す |
| **JWT（Corpus と秘密鍵を共有）** | サービス間の1対1で claims も期限も要らない。鍵の配布と検証コードが増えるだけ。必要になれば `RECALL_API_TOKEN` の検証器を差し替える |
| **Webhook（Recall → Corpus）** | 依存方向の逆流（Corpus ADR 0002）。Recall は Corpus を知らない |
| **ポーリング（Recall が Corpus の DB を読む）** | Recall に Corpus の DB 接続情報が要る。ADR 0001 の「単体で完結」を壊す |
| **非同期キュー（outbox）** | 取り込みは低頻度の管理操作で、同期の遅延を隠す必要が無い。再索引コマンドが回収経路になる。キューは運用対象を1つ増やす |
| **検索失敗時に空を返す（fail-soft）** | `HttpNeneRecordsClient` の先例だが、検索では「根拠なしの回答」になる。フォールバックの方が利用者に正直 |
| **検索失敗時に常に例外（fail-loud）** | チャットが止まる。厳格運用向けに設定で選べる形にした（Decision 5） |
| **soft delete の二段フィルタを省く** | Recall への削除伝達が1回でも漏れると、消した文書が回答に出る。単一テナント・単一利用者では症状が出ない種類の欠陥 |

## Consequences

- Recall 側の作業（Phase 2-A）: migration 0003（`external_id`）、両ストアの `Put`（upsert）と `DeleteByDocument`、HTTP（`external_id`・
  `DELETE /v1/documents/...`・Bearer）、OpenAPI、`recallctl` の追随（`delete-document`・`external_id` の表示）
- Corpus 側の作業（Phase 2-B・別リポ・Corpus 側 ADR 0007）: `src/Recall/`（Config・HttpRecallClient・Null 実装）、
  `RecallChunkSearchRepository`（+ PDO の生存フィルタ）、`IndexedChunkRepository`（デコレータ）、再索引コマンド、
  `SearchServiceProvider` の設定分岐、`.env.example`、テスト
- ADR 0013 の「正解は `eval_key` で持つ」は、`external_id` があれば将来 `external_id` に統一できる。今は触らない
- 評価セット・`alpha`・分割器に影響しない
