# ADR 0015: 合成は加重和（語彙スコアをクエリ内で正規化）とし、`alpha` の既定は 0.8 にする

## Status

accepted (2026-09-02)

## Context

要件定義 F-4 と OpenAPI は、ハイブリッド検索の合成を `alpha*vector + (1-alpha)*lexical` と定め、
`alpha` を利用者が要求ごとに上書きできる契約にしている。既定値 0.7 は**根拠のない当て推量**で、
CLAUDE.md の地雷 7 が「調整済みであるかのように書かないこと」と釘を刺していた（Q-3）。

本 ADR は **2026-09-02 の実測**
（[`docs/benchmarks/2026-09-02-eval-lexical-hybrid.md`](../benchmarks/2026-09-02-eval-lexical-hybrid.md) §3〜§6）
を見てから書いている。

### 実測が示したこと

**加重和は最初、機能していなかった。** `vector_score` の中央値 0.44 に対し、生の `ts_rank` は
0.00016 で**3桁違う**。`alpha=0.7` と `alpha=1.0` で順位が変わったクエリは 58 件中 1 件だけだった。
`ts_rank` のフラグ `32`（`rank/(rank+1)`）で有界化してあったが、rank が小さい領域では
ほぼ恒等写像で、有界化は再スケールではなかった。**これは統合側の指示の誤りで、実装は指示どおりだった。**

語彙スコアを**クエリごとの候補集合内の最大値で割って [0,1] に正規化**した上で合成すると:

| 方式 | `recall@10` | `MRR` |
| --- | ---: | ---: |
| **加重和 + クエリ内正規化（alpha=0.8）** | **0.724** | **0.807** |
| RRF（順位融合・k=60） | 0.694 | 0.723 |
| ベクトルのみ（基準線） | 0.596 | 0.705 |

`alpha` の掃引:

| `alpha` | 0.0 | 0.3 | 0.5 | 0.6 | 0.7 | **0.8** | 0.9 | 0.95 | 1.0 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `recall@10` | 0.620 | 0.654 | 0.678 | 0.688 | 0.708 | **0.724** | 0.721 | 0.666 | 0.596 |
| `MRR` | 0.736 | 0.733 | 0.764 | 0.786 | 0.788 | **0.807** | 0.805 | 0.763 | 0.705 |

最大値から −0.02 以内のプラトーは **0.7〜0.9**。0.95 で急落する。

## Decision

### 1. 合成方式は加重和。語彙スコアは**クエリ内の最大値で [0,1] に正規化**してから合成する

`alpha*vector + (1-alpha)*(lexical / max(lexical in candidates))`。正規化は SQL の中で行い、
候補集合（`org_id` で絞った行）の内側で完結する。ベクトルスコアは正規化しない
（コサイン類似度で既に [−1,1]・実測の値域 0.23〜0.74 で比較可能な尺度になっている）。

**要件定義 F-4 と OpenAPI の `alpha` 契約は変えない。** RRF に負けなかったので、
`alpha` を「重み」として利用者に見せる契約はそのまま生きる。

### 2. `alpha` の既定値は **0.8**（`RECALL_DEFAULT_ALPHA` の既定）

**argmax ではなくプラトーで選ぶ。** 0.7〜0.9 のプラトーの中心であり、たまたま最大値でもある。
端（0.9）は 0.95 で急落する崖の隣なので選ばない。0.7 は「当て推量が当たっていた」のではなく、
プラトーの端であり、中心の 0.8 より `recall@10` で −0.016・`MRR` で −0.019 低い。
差はゆらぎの範囲（1クエリ＝0.017）で、**0.7 が悪いから変えるのではなく、根拠のある値へ置き換える**
ためである。

### 3. この値は**条件付き**である。次のどれかを変えたら測り直す

- 語彙スコアの正規化方式（クエリ内最大値以外にしたら `alpha` の意味が変わる）
- 分割器（`Tokenizer.ID()` が変わったら）
- 埋め込みモデル（`Embedder.ID()` が変わったら）
- 候補集合の作り方（項目 7 で HNSW を入れ、全行に順位を振らなくなったら。RRF の評価も変わりうる）

コードのコメントや文書で `alpha=0.8` を「最適値」と書かず、「2026-09-02 の評価セット・
`bge-m3:1024`・bigram・クエリ内正規化の条件で選んだ値」と書く。

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| **RRF（順位融合）を既定にする** | 実測で加重和に負けた（0.694 vs 0.724・MRR 0.723 vs 0.807）。加えて `alpha` を無意味にするので F-4 と OpenAPI の契約変更を伴う。⚠️ ただし本測定の RRF は古典的 RRF と条件が違う——索引が無く全行に順位を振るため、語彙が当たらない行が同順位に固まり、語彙1位が買えるのは1つ順位を上げることだけだった（`TestRRFGivesLittleCreditWhenFewDocumentsMatch` が固定）。**候補集合を絞る構成では再評価の余地がある。** 実装は計測用として残す |
| **`ts_rank` のフラグ `32` で有界化して済ませる** | 有界化は再スケールではない。実測で加重和がほぼ効いていなかった原因そのもの |
| **語彙スコアを大域的な定数で割る** | `ts_rank` の値域はコーパスとクエリ長に依存し、定数は別コーパスで壊れる。クエリ内正規化は候補集合だけで閉じる |
| **ベクトルスコアも min-max 正規化する** | ベクトルは既に比較可能な尺度で、候補内 min-max にすると「全候補が遠い」クエリでも1位が 1.0 になり、絶対的な確信度の情報を捨てる。⚠️ 測っていない却下なので、`alpha` の再測定の機会に候補として残す |
| **`alpha` を argmax（0.8 のうち最大の点）で決める** | 結果は同じ 0.8 だが、選び方が違う。argmax はゆらぎに引きずられる。プラトーで選ぶ規約を今後の再測定にも適用する |
| **0.7 を据え置く** | プラトーの中には入っているが端であり、「根拠が無い」状態を「根拠のある値」で置き換える機会を逃す |

## Consequences

- **利得**: `recall@10` 0.596 → 0.724（+0.128・ゆらぎの7倍以上）、`MRR` 0.705 → 0.807
- **費用**: 語彙スコアの正規化に窓関数 `MAX() OVER ()` 相当が1段増える。索引なしの全探索では
  無視できる（latency の正本は rounds=5 で取り直す。本 ADR の測定は rounds=1）
- **文書の更新**: CLAUDE.md 地雷 7・要件定義 Q-3・`config.go` の `DefaultAlpha` のコメント・
  `httpapi/search.go` の「根拠はまだ無い」コメント・OpenAPI の `alpha` 説明を、本 ADR を指す形に直す
- **地雷**: `alpha` を変えるだけの変更は今後も「実測を見て ADR を書く」経路を通す。
  CLAUDE.md 地雷 7 は「0.7 に根拠は無い」から「0.8 は条件付き（§ Decision 3）」へ書き換える
